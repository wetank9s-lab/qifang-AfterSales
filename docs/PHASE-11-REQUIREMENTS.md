## 0. 文档权威与执行纪律

本文件是 Phase 11 的产品与开发契约。它的目标不是重新设计既有状态机、安全模型或短信体系，而是把已经完成的售后引擎升级成一套门店人员能高效使用、总部能长期管理、客户特别是中老年客户能方便报修的正式产品。

### 0.1 开工前必须做的事

开发者开始写代码前必须：

1. 先读 `docs/PHASE-10.md` 顶部当前冻结状态，确认 Phase 10 仍为 `RELEASE HOLD`。
2. 读本文件全文，不以旧摘要、旧“下一步”、历史阶段计划替代本契约。
3. 对照当前源码做一次 **read-only preflight**，只记录“源码事实与本契约是否一致”。
4. 若只是实现细节不同，不得重新向产品方开放产品决策；按本契约落地。
5. 只有发现**真实源码事实使本契约无法成立或会破坏冻结安全边界**时，才停止并回报。

### 0.2 实施纪律

- 不开 P11-D、P11-X 之类临时新阶段；只使用 P11-0～P11-7。
- P11-0～P11-7 是实施组织，不是逐段审批点；可连续推进。
- 不回头重验已经冻结的 Phase 5～9，除非 Phase 11 的修改直接触碰其不变量。
- 不允许为了“全绿”修改业务语义或扩大豁免名单。
- 关键写操作继续使用业务 Service / Action，不允许通过 NocoBase 原生 Edit 直接写状态、师傅、金额、Token 等核心字段。
- 任何新匿名能力必须保持：高熵凭证、服务端权限判断、日志脱敏、私有文件、限流、幂等。
- 任何新增配置必须有真实运行时消费者；禁止出现“后台有配置项，但代码从未读取”的假能力。
- Phase 11 完成标准以真实用户任务是否顺畅为主，不以断言数量为主。

# 1. 产品定位

系统正式定位为：

> **15 家家电门店的售后服务管理平台**

- 维修
- 安装
- 调试 / 保养

客户 H5 仍保持简单，只提供：

- 报修

门店员工人工新建时，才显示完整的服务类型。

# 2. 必须继续保持的既有不变量

以下语义不得因 UX 重构被破坏：

1. 主工单状态仍然只有六个：
   - `NEW`
   - `PROCESSING`
   - `WAIT_STORE_CONFIRM`
   - `WAIT_FEEDBACK`
   - `CLOSED`
   - `CANCELLED`

2. 师傅提交服务结果不等于工单完成：
   - 师傅提交 → `WAIT_STORE_CONFIRM`
   - 门店审核后 → `WAIT_FEEDBACK`

3. 低评分或收费不一致仍然：
   - `escalated = true`
   - 工单重回 `PROCESSING`
   - 不直接关闭

4. 历史 Visit 不可覆盖：
   - 责任主体变化必须保留历史
   - 改派产生新的 Visit 或等价不可覆盖记录
   - 旧记录保持可追溯

5. 客户 / 师傅继续无系统账号。

6. 门店数据范围继续由服务端 `storeScope` / PermissionService 控制，不能只靠隐藏菜单。

7. Token 明文不得入库、不得写日志、不得进 TicketEvent metadata、不得进导出。

8. 图片 / 音频 / 视频继续私有存储，不能给永久公网 URL。

9. 当前预计上门字段仍为**日期语义**，不是精确到分钟的到达承诺；没有签到/GPS 就不得输出“准时到达率”。

# 3. Phase 11 的核心用户任务

## 3.1 门店售后人员

门店人员登录后应该立即知道：

> 今天有哪些服务单需要我做什么？

而不是判断：

> 我要点受理、派工、改派还是改约？

门店人员最常见任务：

- 看新服务单
- 决定怎么处理
- 安排自有师傅
- 交厂家 / 第三方
- 电话直接解决
- 转给其他门店
- 取消
- 记录跟进
- 修改非核心客户资料
- 审核师傅结果
- 人工新建电话 / 微信 / 到店服务单
- 查客户历史售后
- 导入历史 Excel

## 3.2 总部售后

总部人员最关心：

- 哪家门店新单没人处理
- 哪家门店厂家单长期没跟进
- 哪些预约已过期
- 哪些师傅已提交但门店没审核
- 哪些低分 / 收费异常返工没有再次安排
- 各店积压量和处理时效

## 3.3 总部管理员

管理员需要自己维护：

- 门店
- 门店人员授权
- 服务时效
- 超时短信联系人
- 业务参数
- 历史数据导入模板

不再依赖开发者改 seed / SQL。

## 3.4 客户

特别针对中老年客户：

- 尽量少打字
- 能说、能拍、能录
- 提交后知道是否成功
- 能从短信重新找到服务进度
- 不需要注册账号

## 3.5 师傅

师傅通过一次性 H5：

- 能直接看到客户姓名
- 能直接拨打完整手机号
- 能看到服务地址
- 能看报修内容
- 能查看客户上传的照片 / 语音 / 视频
- 填服务结果并提交

# 5. 门店工作流重构：取消“受理”按钮

## 5.1 用户界面不再出现“受理”

门店列表中不得再出现：

- 查看
- 编辑
- 删除
- 详情
- 受理
- 派工
- 改派
- 改约

这种按钮墙。

正式服务单不得提供原生删除。

行本身可点击进入服务详情；每行最多一个主业务按钮：

| 当前业务状态 | 主按钮 |
|---|---|
| NEW | **处理** |
| PROCESSING | **跟进** |
| WAIT_STORE_CONFIRM | **审核结果** |
| WAIT_FEEDBACK | **查看** |
| CLOSED | **查看** |
| CANCELLED | **查看** |

## 5.2 NEW 的“处理”窗口

门店点击 **处理** 后，只看到五种现实选择：

1. **安排上门**
2. **交厂家 / 第三方处理**
3. **电话 / 门店直接解决**
4. **转给其他门店**
5. **客户取消**

这一步本身即代表门店已实际开始处理，不再要求先点一次“受理”。

## 5.3 首次响应语义

保留数据库字段 `first_response_at`，但产品语义调整为：

> 门店第一次执行真实处理动作的时间。

以下动作若 `first_response_at` 尚为空，应原子写入：

- 安排上门
- 交厂家 / 第三方
- 电话 / 门店直接解决
- 取消
- 其他明确进入处理的动作

同时首次设置 `handler_user_id`。

旧 `accept` action 可以保留兼容已有脚本/历史调用，但：

- 不出现在业务 UI
- 不再是正常流程前置
- 新功能不得依赖“先 accept 才能继续”

## 5.4 转店后的 SLA 基准

新增或等价实现：

`current_store_entered_at`

语义：

- 新建服务单：等于创建时间
- 转入新门店：更新为转店时间
- `first_response_at` 仍记录整个工单生命周期中的首次真实响应，不因转店重置

这样总部可以分别分析：

- 全局首次响应
- 当前门店接手后多久开始处理

转店时应考虑把当前处理人清空或按现有权限模型重新归属，不能让原门店处理人继续成为新门店的当前责任人。

# 7. 服务方式重构

## 7.1 自有师傅上门

选择“安排上门”时必须：

- 服务地址非空
- 师傅姓名
- 师傅手机号
- 预计上门日期

随后：

- 创建 Visit
- 生成师傅 Token
- 发送师傅短信
- 按现有语义通知客户
- 状态进入 / 保持 `PROCESSING`

## 7.2 厂家 / 第三方

现实业务允许门店只知道：

> 已报给海尔售后 / 美的售后 / 某第三方服务商

而不知道具体师傅。

因此：

- `provider_name` 必填
- 具体师傅姓名 / 手机号可以为空
- 预计处理日期可以为空或选填
- 不得为了过校验逼员工填假姓名 / 假手机号

### 具体师傅后来才明确

当厂家告知具体师傅后：

- 记录“厂家已指派具体师傅”
- 创建或切换为一条新的具体责任 Visit
- 给该师傅签发 H5 Token
- 历史 provider-only 责任记录不得被静默覆盖

### 厂家最终没有提供具体师傅

门店可执行：

**登记厂家处理结果**

填写：

- 处理结果
- 处理说明
- 是否收费
- 收费金额（如收费）

该动作由门店登记外部服务结果，完成后直接进入正常评价流程，不要求伪造师傅手机号，也不要求同一门店再审核自己刚录入的结果。

## 7.3 电话 / 门店直接解决

正式实现 `remoteComplete` 或等价业务动作。

填写：

- 处理结果
- 处理说明
- 是否收费
- 收费金额

要求：

- 不生成师傅 Token
- 不发师傅短信
- 保留一条可审计服务记录
- 状态从 PROCESSING 进入 WAIT_FEEDBACK
- 后续评价 / 低分重开规则完全复用现有闭环

# 8. 服务单数据模型升级

以下是业务必需字段；允许开发者在保持语义的前提下选择具体迁移形式，但不得把可查询业务字段全部塞进 `extra_json`。

## 8.1 `serviceTickets` 建议新增 / 调整

### 服务类型

现有 `ticket_type` 保留内部字段名，但扩展枚举：

```text
repair         维修
installation   安装
maintenance    调试 / 保养
relocation     移机 / 拆机
complaint      投诉
other          其他
```

客户匿名 H5 只允许提交：

- `repair`
- `complaint`

门店人工新建可使用全部六种。

### 新字段

- `service_address`：服务地址，客户提交选填；安排上门前必填
- `appliance_category`：家电类型
- `brand_model`：品牌 / 型号，选填
- `urgent`：是否紧急
- `current_store_entered_at`：当前门店接手时间
- `next_follow_at`：下次跟进日期 / 时间
- `progress_ref`：客户进度链接引用值，唯一；单独 ref 不能完成鉴权
- `progress_revoked_at`：可选，用于主动失效
- `media_evidence_hold`：是否保留客户媒体证据
- `media_evidence_hold_reason`
- `media_evidence_hold_at`
- `media_evidence_hold_by`

`content` 不再要求 5 字以上。允许空字符串 / null，但业务层必须保证：

> 文字或至少一个有效客户媒体，至少存在一种。

## 8.2 家电分类

建议固定枚举：

```text
air_conditioner    空调
refrigerator       冰箱
washer             洗衣机
tv                 电视
kitchen_bath       厨卫电器
small_appliance    小家电
other              其他
```

这是简单分类，不建立 ERP 商品档案。

## 8.3 `serviceVisits`

现有“技师姓名 / 手机 / 预计上门日期永远非空”的数据库假设必须调整成**按服务方式条件校验**。

允许以下三种责任形态：

1. `inhouse`
   - technician_name 必填
   - technician_mobile 必填
   - expected_visit_at 必填
   - Token 必须存在

2. `manufacturer / third_party` provider-only
   - provider_name 必填
   - technician_name / mobile 可为空
   - Token 为空
   - 可以后续产生具体师傅 Visit，历史不可覆盖

3. `remote`
   - technician_name / mobile 为空
   - Token 为空
   - `is_remote=true`

# 10. 客户 H5 多媒体报修

## 10.1 页面目标

页面标题从“填报修表单”转成：

> **告诉我们哪里有问题**

提供四种大入口：

- 🎙 说一说
- 📷 拍照片
- 🎥 拍视频
- ✏️ 写几句话

规则：

> 四种方式至少一种即可，文字不再必填。

## 10.2 媒体限制

- 图片：0 或 1～3 张
- 语音：最多 1 段，≤ 60 秒
- 视频：最多 1 段，≤ 30 秒
- 可以组合提交
- 图片继续做 magic bytes 校验、隐私元数据清理
- 音视频必须同时校验：
  - 文件大小
  - MIME / 容器白名单
  - 实际可读取性
  - 时长
- 不信任浏览器 Content-Type / 扩展名
- 具体字节上限应形成明确可配置值并由 H5 回显；禁止无限上传

## 10.3 录音交互

不要使用“按住说话”作为唯一方式。

使用：

```text
开始录音
停止录音
播放
重新录
删除
```

视频 / 图片上传后必须有明确缩略图 / 封面 / 上传状态。

## 10.4 浏览器兼容

优先使用浏览器媒体能力，但必须渐进增强：

- 支持 MediaRecorder 时用内置录制
- 不支持时退化到手机系统拍摄 / 文件选择

# 12. 客户进度查询

## 12.1 找回方式

客户创建服务单成功后：

1. 成功页显示 **查看处理进度**
2. 系统发送一条确认短信
3. 短信包含独立进度链接
4. 客户关闭浏览器后可从短信重新进入

进度 Token 不得复用：

- 评价 Token
- 师傅 Token
- Ticket ID

## 12.2 凭证设计

不得把长期有效的完整进度 Token 明文存入：

- serviceTickets
- idempotencyRecords.response_json
- SmsLog
- TicketEvent
- 日志

建议：

```text
progress_ref + HMAC-SHA256 signature
```

- DB 保存随机 `progress_ref`
- 使用独立 `PROGRESS_SIGN_SECRET`
- 完整 URL 由服务端确定性生成
- 只有 `ref + valid signature` 才能读取
- 比较使用安全比较
- 不信任仅有 ref 的请求

建议路由：

```text
/p/{signed-token}
→ /h5/customer/progress/{signed-token}
```

不得放 query string。

Nginx / app 日志必须使用固定 normalized route，不记录明文 Token。

## 12.3 有效期

- 工单进行中：有效
- CLOSED / CANCELLED 后：继续有效 30 天
- 30 天后：返回友好“链接已过期，请联系门店”
- 支持安全主动吊销

## 12.4 客户可见内容

只返回客户需要的信息：

- 服务单号
- 门店名称
- 当前客户友好状态
- 服务类型 / 家电类型 / 品牌型号
- 客户提交内容摘要
- 当前预约日期
- 当前服务人员姓名 / 联系电话（有时）
- 门店售后电话
- 可公开的进度节点
- 是否可评价 / 已完成

不得返回：

- 内部用户 ID
- 内部备注
- 完整 TicketEvent metadata
- Token / hash
- SMS 内部记录
- ACL / 角色信息
- 其他门店数据

## 12.5 客户状态文案

不要直接暴露六个技术状态。

使用类似：

- 已提交，等待门店处理
- 门店正在处理
- 已安排上门服务
- 已交厂家 / 第三方处理
- 服务人员已提交，等待门店确认
- 服务已确认，等待您的评价
- 正在重新安排处理
- 已完成
- 已取消

## 17.1 五类时效

起点：

终点：

### E. 返工待处理

# 21. 已上传真实售后数据对导入功能的约束

当前样本共 7 个门店文件：

- 5 个 `.xlsx`
- 2 个旧 `.xls`

- 一个商品字段包含多台设备
- 列名写“处理日期”，实际内容却是“回访已好 / 等配件 / 用户不修”
- 完工日期可能早于接件日期
- 安装 / 维修 / 配送 / 销售资料混在不同格式中
- 备注里承载多次跟进
- 老 `.xls` 文件仍在使用

# 33. 安全边界

## 33.1 客户媒体

- 私有目录
- 不走永久公开 URL
- 受控读取
- 服务端 sniff / whitelist
- 图像继续清元数据
- 音视频不信任扩展名
- 文件名不能决定落盘路径
- 防目录穿越
- 限额 / 限速
- 上传 session 过期
- 未绑定媒体清理

## 33.2 师傅查看客户资料

因为产品已决定向当前师傅展示姓名、完整手机号和地址，所以必须同时做到：

- 只有当前有效 Visit Token
- 最小字段返回
- 改派 / 取消 / 转店立即失效
- 路径 Token 不进日志
- 完整手机号不进日志
- 媒体 URL 不永久公开
- 响应 `Cache-Control` 不允许长期公共缓存

## 33.3 历史导入

真实 Excel 含大量 PII：

- 导入原文件不得提交 Git
- 测试 fixture 必须脱敏 / 造数
- 导入错误日志不得打印整行客户数据
- raw_json 只存在数据库内并受 HQ / storeScope 控制
- 导入报告对门店只显示其门店数据
- 导出继续遵守现有安全导出边界

# 36. 自动化门禁原则

Phase 11 需要新增测试，但不要重新制造“断言数量竞赛”。

重点门禁应证明：

1. **工作流唯一入口**  
   NEW 不需要 accept；第一次真实处理正确写 first_response。

2. **权限**  
   B-8 被真正关闭，不是只隐藏 UI。

3. **多媒体安全**  
   类型 / 大小 / 时长 / 私有存储 / session 绑定 / orphan 清理。

4. **匿名进度 Token**  
   随机 / 篡改 / 过期 / 关闭+30天 / 日志零明文。

5. **提醒幂等**  
   scheduler 重叠执行同一周期只有一条 open alert / 一次短信。

6. **历史导入**  
   同文件 / 同 batch 可重放，不出现重复历史数据。

7. **历史隔离**  
   导入 3000 条旧数据不能让当前 SLA / Dashboard 突然全部爆红。

8. **媒体清理**  
   普通到期媒体真删除；evidence hold 不删除。

9. **客户端动作矩阵**  
   列表每行只能出现一个主动作；未知状态不错误给按钮。

10. **关键回归**  
    评价、师傅提交、门店确认、低分重开、收费不一致、短信回执继续保持原冻结语义。

反向门应验证“判据真的会红”，但不要为每一个普通 UI 字段都造重型 reverse gate。
