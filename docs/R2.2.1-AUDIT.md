### 2.3 Konsta 5.5.0 的 Liquid Glass 实际落点（逐文件核实）

| 组件 | 文件 | 玻璃实现 | 本应用是否受影响 |
|---|---|---|---|
| `Glass`（独立组件） | `shared/classes/GlassClasses.js` | `.k-glass + backdrop-blur-lg` | ❌ 未使用 |
| `Navbar` | `NavbarClasses.js:42` | `bgBlur` 层 `backdrop-blur-[2px]` + `mask-b-to-100%` | ⚠️ **这是真正的风险点** |
| `Toolbar`/`Tabbar` | `ToolbarClasses.js:21` | `bgBlur` 层 `backdrop-blur-[2px]` + `mask-t-from-50%` | ⚠️ **这是真正的风险点** |
| `Popover` | `PopoverClasses.js:48` | `bg-ios-light-glass backdrop-blur-lg` | ❌ 未使用 |

**关键事实（必须写清楚，避免过度声明）**：

1. 产物 CSS **确实生成了** `.backdrop-blur-[2px]` 规则（已实测 grep 命中）。
2. 但**组件是否渲染那一层，由 props 决定**。实测 `dist/assets/style-BqsGLhx-.css`
   中 `mask-b-from-50%` / `mask-t-from-50%` **命中 0 次** ⇒ 说明这两个 mask 工具类
   在产物里根本没生成 ⇒ **`bgBlur` 那一层当前没有渲染**。
3. 结论：**当前生产没有可见的毛玻璃**，但 `bgBlur` 是 Konsta 的默认能力，
   任何一次"给 Navbar 加个 scroll-edge 效果"的改动都会把它带回来。
   ⇒ 必须在设计系统里**显式禁用**（`BgBlur` 不渲染 / 或用 CSS 兜底覆盖），
     而不是依赖"现在恰好没开"。

**Navbar / Toolbar 的另一处 glass 痕迹**：
```js
// NavbarColors.js
bgIos: 'bg-gradient-to-b from-ios-light-surface to-transparent'   // #efeff4 → 透明
// ToolbarColors.js
bgIos: 'bg-gradient-to-t from-ios-light-surface to-transparent'
```
这是 **iOS 26 的 scroll-edge fade**，不是经典 iOS 的"实心白 + hairline"。
但 `AppShell.tsx` 给 `PageHeader` 传了 `className="top-0 sticky bg-svc-surface"`，
Tailwind 的 `bg-svc-surface`（实心白）**覆盖了** gradient（同为 `background-image` 附近优先级，
实测视觉上是实心白）⇒ 当前观感正确，**属于"巧合正确"而非"设计正确"**。

### Lens 1 · Accessibility（关键门槛）

#### A-01 · Critical · 三级文字 `#8E8E93` 在浅灰底上仅 **2.92:1**

- **位置**：`src-mobile/src/design/tokens.ts` → `'ink-3': '#8E8E93'`，
  实际使用 23 处 `text-svc-ink-3`（`text-[11px]` 占多数）
- **实测**（本次现算 WCAG）：
  ```
  #8E8E93 on #FFFFFF   = 3.26:1  ✗
  #8E8E93 on #F2F2F7   = 2.92:1  ✗
  #8E8E93 on #F7F7FA   = 3.05:1  ✗
  ```
- **指南**：`accessibility.md › Vision` —— "Up to 17 pts / All / **4.5:1**"
- **现实后果**：档案编号、建档时间、"已经到底了"、"共 N 条"这些**都是 ink-3**。
  门店销售靠档案编号核对（用户第 7.1 条明确要求"档案编号放次要位置"，
  但"次要"不等于"看不清"）。
- **根因**：`tokens.ts` 的注释自己写着「iOS `placeholderText`，不受正文对比度约束」——
  这句**是错的**：placeholder 不受约束，但 ink-3 大量用于**非 placeholder 的真实文字**。
- **修法（待第二阶段落地）**：拆成两个 token
  - `ink-3 = #6E6E73`（白 5.07 / 灰 4.54 / surface-2 4.74）→ 用于"真实但次要的文字"
  - `placeholder = #8E8E93`（保持）→ 只用于输入框占位符
- **判据**：`design-parity.mjs` 新增断言「`ink-3` 在 `bg`/`surface`/`surface-2` 三底上均 ≥4.5」，
  且**先做变异验证**（把值改回 #8E8E93，断言必须变红）。

#### A-02 · High · 主色 `#007AFF` 作为**文字**时仅 **4.02:1**

- **位置**：`text-svc-brand` 用于文字链接/可点文字，共 18 处，例如
  `ArchiveList.tsx`「清空」「看照片」、`ServiceSearch.tsx`「查看全部」
- **实测**：
  ```
  #007AFF on #FFFFFF = 4.02:1  ✗（<4.5）
  #007AFF on #F2F2F7 = 3.60:1  ✗
  ```
- **指南**：`accessibility.md › Vision`（4.5:1）+ `color.md › Inclusive color`
  （"insufficient contrast can cause icons and text to blend with the background"）
- **关键区分**（不能一刀切）：
  - 作为**按钮填充底色**（白字压在上面）：`#007AFF` 上是 4.02:1，
    但按钮文字通常是 **17px Semibold**（Large 档）⇒ **3:1 门槛**（`accessibility.md` 表第三行
    "All / Bold / 3:1"）⇒ **填充按钮达标** ✅
  - 作为**13–15px 的纯文字**：**不达标** ✗
- **修法**：**新增第三个蓝**，不改 iOS 系统蓝本体
  ```
  brand        #007AFF  仅用于填充底、图标、进度条、焦点环（非文字）
  brand-text   #0062CC  仅用于可点文字（白 5.80 / 灰 5.20 / 白字在其上 5.80）
  brand-strong #0062CC  按下态（已有）
  ```
- **判据**：新增断言「所有 `text-svc-brand` 实际渲染出的**文字**元素，
  其前景/背景对比度 ≥4.5」——这条要用浏览器实测（computed style 取样），
  不能用源码 grep（grep 分不清"底色"和"文字"）。

#### A-03 · High · 触控目标在 4 处实际小于 44×44

`app.css` 已强制 `.k-button { min-height: 44px }` 与 `[data-svc-touch]`，

#### A-04 · Medium · 最小字号 `text-[10px]` / `text-[9px]` 出现在真实信息上

### Lens 2 · Platform conventions（平台约定）

#### P-01 · High · 服务类型选择用的是**胶囊按钮组**，不是 iOS Segmented Control

- **位置**：`src-mobile/src/components/Form.tsx:199` `SegmentedField`
  ```tsx
  className={`min-h-touch rounded-full border px-3.5 ...`}
  ```
- **实际观感**：一排**大小随文字长度变化**的胶囊（"上门服务"4 字 vs "暖通工程"4 字恰好等宽，
  但"送货安装/安装调试/维修检测/清洗保养/使用指导/其他"六个**长度不一**）。
- **用户明令**（第六节）：「服务类型/服务内容选择控件采用**统一分组选择器或网格选择**，
  不能再用大小不一的椭圆选项。」
- **指南**：`segmented-controls.md › Best practices` ——
  "In general, keep segment size consistent. When all segments have equal width,
  a segmented control feels balanced."；"no more than about five segments on iPhone"
- **两个问题**：
  1. **形状**：`rounded-full` 胶囊 ≠ iOS segmented（后者是 **9–10px 连续圆角容器**）
  2. **数量**：服务内容有 **6 项 > 5** ⇒ iOS 建议用**网格/列表**而非 segmented
- **修法**：
  - `服务类型`（2 项）→ 真正的 **Segmented Control**（等宽两格、轨道 `#F2F2F7`、
    选中白底 + 浅阴影、容器圆角 9px）
  - `服务内容`（6 项）→ **2 列网格**（等宽等高 48px，圆角 10px，选中蓝底白字 + 勾）
- **判据**：
  - DOM 断言：`.qf-segmented` 下每个 segment `getBoundingClientRect().width` 极差 ≤ 1px
  - 视觉断言：所有选项按钮 `border-radius` ≤ 12px（**禁止 9999px**）

#### P-02 · High · 用户明令禁止的"椭圆主操作按钮"目前**没有**，但"椭圆选项"遍布

- **主按钮实测达标**：Konsta `Button` 默认 `shape="square"` ⇒ `rounded`（8px）。
  实测 `ButtonClasses.js`：`rounded: segmented && !segmentedStrong ? '' : 'rounded-full'`
  **只在传 `rounded` prop 时**才 `rounded-full`。三个主页面**均未传** ⇒ 主按钮是 8px 圆角 ✅
- **但 `rounded-full` 全仓 18 处**，其中**交互元素 7 处**：
  ```
  Form.tsx:199          SegmentedField option   ← 见 P-01
  ArchiveList.tsx:338   FilterPill              ← 筛选条件
  TicketList.tsx:295/338 筛选 pill
  TicketDetail.tsx:227  可点 chip
  Feedback.tsx:53       ServiceStatusBadge      ← 状态徽标（这个可以保留，见下）
  Domain.tsx:201        「待你处理」标记
  ```
- **区分处理**（不能一刀切）：
  - **状态徽标**（`ServiceStatusBadge`）保留胶囊 —— iOS 里 tag/badge 就是胶囊，
    且它不是操作，是信息标注。`lists-and-tables.md › Content` 允许。
  - **筛选条件 / 可点选项 / 可点 chip** ⇒ 改 10px 圆角矩形。
    理由：`buttons.md › Style` 要求"用 style 而不是形状区分主次"，
    而**胶囊 + 描边**在视觉上更像"标签"而不是"可点的筛选器"。
- **判据**：可点元素（`button`/`[role=button]`）中，`border-radius` 允许值集合
  ⊆ `{0, 8px, 9px, 10px, 12px, 14px, 44px(图标按钮), 9999px(仅状态徽标)}`；
  且 9999px 只允许出现在 `class` 含 `qf-badge` 的元素上。

#### P-03 · Medium · `search-fields.md › Best practices` 要求"边打字边搜"，当前是回车才搜

- **位置**：`ServiceSearch.tsx` 顶部注释明确写「**不**是边打字边发请求」，理由是并发乱序。
- **指南**：**"If possible, start search immediately when a person types."**
- **判断**：**这不是要推翻现状**。指南说的是 "if possible"，
  而本项目的并发乱序风险是真实的（两个 `:list` 打不同 API）。
- **但**：`ArchiveList.tsx` 的 Searchbar **是完全可控的**（单接口 + `seq` 序号守卫），
  却也没有 debounce。**同一个"搜索"在三个页面有三种行为**：
  ```
  ArchiveList     输入即改 state → 但 load 依赖 kw → 每次输入都发请求（无 debounce）
  ServiceSearch   回车才搜
  ArchiveQuery    手动提交
  ```
- **修法**：统一为 **300ms debounce + `seq` 守卫**（已有 `seq` 的页面直接复用），
  并在设计系统里只留一个 `QFSearchField`。
- **判据**：三个页面的搜索行为由**同一个组件**产生（grep 只允许 1 处 `<input ... search`）。

#### P-04 · Medium · `PageHeader` 的返回按钮用了文字"返回"，iOS 用符号

- **位置**：`AppShell.tsx` `PageHeader` → `<NavbarBackLink text="返回" />`
- **指南**：`toolbars.md › Navigation` —— "**Prefer the standard symbols** for each,
  and don't use a text label that says *Back* or *Close*."
- **现实权衡**：iOS 的返回按钮通常是"‹ 上一页标题"，纯符号在中文语境下
  确实有用户不认识。**Konsta 的 `NavbarBackLink` 默认就是"‹ + text"**，

## 一、第 13 条：统一中文文案（新门禁 `verify-error-i18n.mjs` · 6/6）

### 1.1 为什么这件事必须变成静态判据

「界面不出现英文报错」**没有任何运行期信号** —— 它只在断网、无权限、版本冲突这些
**低频路径**上才暴露，而开发时天天走的是成功路径。换句话说：这类缺陷只能靠
**人偶然撞见**才会被发现，除非把它变成静态判据。

### 1.2 新增 `ERROR_CODE_TEXT`（八个点名码逐条写死）

| 错误码 | 文案要点 |
|---|---|
| `ARCHIVE_STAGE_ORDER` | 暖通必须按顺序做：勘察 → 方案 → 布管 → 装设备 → 试机 → 验收 |
| `ARCHIVE_STAGE_PHOTO_REQUIRED` | 勘察 / 布管 / 装设备 / 验收 四步都要有照片 |
| `ARCHIVE_STAGE_PHOTO_LIMIT` | 每个阶段最多 6 张 |
| `ARCHIVE_STALE` | 数据已更新，本次修改未保存；**你填的内容还在页面上** |
| `ARCHIVE_QUERY_BAD_MOBILE` | 请填 11 位手机号，只填数字 |
| `ARCHIVE_QUERY_RATE_LIMITED` | 查询有次数限制，请稍等 |
| `ARCHIVE_QUERY_UNAVAILABLE` | 服务维护中，或直接到门店前台查验 |
| `STORE_USER_NOT_LINKED` | 账号没绑门店，请联系总部管理员在「门店账号管理」里绑定 |

**关键顺序问题**：`describeQFError` 里错误码表必须是**第一条分支**（判据 E4）。
否则 `ARCHIVE_STAGE_PHOTO_REQUIRED`（常为 400）会被通用 400 分支抢走，
只输出「请求未完成」这种废话。同理，**429 先于权限判**是有意为之：限流与无权同时出现时，
告诉用户"太频繁"是对的，让他重试即可，不必惊动管理员。

### 1.3 变异测试（4 个变异全部变红）

```

✓ 删掉账号未绑定码       → E1-eight-codes 变红
✓ 把某条 title 改成英文   → E2-chinese-only 变红
```
