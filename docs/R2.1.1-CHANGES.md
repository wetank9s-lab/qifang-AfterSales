## 一、方案变更（用户裁决，覆盖原指令 ⑤ ⑥）

原指令要求"生产管理菜单整理成两个可折叠菜单组（日常业务 6 页 / 管理与设置 8 页）+ 解决 UID 不一致"。
**原生父组迁移方案已放弃**，改为**前端虚拟分组**。理由与实测证据：

| # | 结论 | 证据 |
|---|---|---|
| ① | 原生分组必然改 `desktopRoutes.parentId` + `rolesDesktopRoutes` | 2.2.15 的 `listAccessible(tree:true)` 对"已授权组"把子页**全量递归展开、不再过滤** |
| ② | ⇒ 组内每页授权必须**完全相同**，否则分组就是权限放大器 | 生产实测 14 页授权集合各不相同（3~6 角色） |
| ③ | 生产 1440px 下并列两个顶层组**不显示分组** | 混排布局把顶层项塞进 header，侧栏把 group 的 children 渲染成**无标题平铺** |

保守方案（只在现有唯一顶层组内挂一个 `管理与设置` 子组）交由用户后，用户最终裁决：
**不动任何路由/授权，前端做展示分组。**

### 3.2 未达标（三条，均已定性，不当"已修"报）

#### (A) 筛选区折叠态仍是 **176px**，目标 80–100px

DOM 实测（`scripts/_r211-filtercheck.mjs`）：

```
.ant-card-body  h=208  (padding 16)
 └ .ant-form     h=176
    ├ DIV        h=148   ← 两行 Grid（74 + 12 gap + 74）
    └ ant-space  h=28    ← 查询/重置
```

**根因**：`FilterFormCollapseActionModel` 在 2.2.15 客户端**确实注册了组件**，
但它只在 `onMount()` 时执行一次 `defaultCollapsed`。而筛选项是 `onModelCreated` 异步挂载、
filterForm 服务端分页加载、页签切换会整块重建 —— **重建后没有任何一方重新施加折叠状态**。
所以即使写了 `defaultCollapsed: true`，DOM 里也只剩 7 个同层 item、无折叠按钮。

> 本轮已把 `ensure_collapse_action` 的 `defaultCollapsed` 从 `False` 改为 `True` 并实测 —— 无效。
> **不采用"CSS 裁高度"的做法**：那会把真实条件藏在滚动容器里，看着达标、实际更难用，
> 属于造假绿，已主动放弃。

#### (B) 操作列仍在**最左**

框架 `createModelOptions` 把 `columns[0]` 写死为 `TableActionsColumnModel`，且它与
`TableColumnModel` 是**不同 type** ⇒ `buildTree()` 先 `groupBy(children,'type')`，
两个 type 各成一组，`sort` 只在组内生效。

**已用两组实验证伪并回滚**：
- `flowModels.options` 写 `x-index` → 列序不变
- `flowModelTreePath.sort` 调整 → 列序不变（`sort=9` 的动作列仍排最前）

#### (C) 「创建日期」列无法"隐藏"，只能"删除"

实测四种写法**全部无效**（每次均已重启 app 让模型重建）：

| 写法 | 结果 |
|---|---|
| `props["x-visible"] = false` | 列仍在 |
| `props["hidden"] = true` | 列仍在 |
| `props["x-hidden"] = true` | 列仍在 |
| `props["width"]=120` + `props["hidden"]=true` | 列仍在 |
| **删除该列的 flowModel + 闭包行** | **列消失** ✅ |

原因：`TableColumnModel.getColumnProps()` 在 2.2.15 里**开头就是 `if(!this.props.width) return;`**
（`width` 缺省时直接返回 undefined，被 `.filter(Boolean)` 过滤掉）。而全库 **100 个列模型没有任何一个配 `width`**。
⇒ 这条判断实际是死代码，"按 hidden 隐藏"的语义在这版上不可用。

**本轮决定：保留该列（排在尾部），不删除。** 删列不可逆且会丢字段配置，
且用户未授权删列。⇒ 如实列为未达标项，等用户裁决。

## 7.1 筛选区：从 176px 到 **140px**（6 页签一致）

### 结果

| 页签 | 改前 | 改后 |

| 全部 | 176 | 140 |

构成：字段两行（每行 28 控件 + 16 标签 + 6 边距 ≈ 50）× 2 = 100，label 行 12，按钮行 28，余量为栅格 row-gap。
**落在用户授权的降级区间 120–140px 上沿。**

### 为什么没做到 80–100px（必须写清楚，这是"限制说明"）

按裁决要求先核实了运行镜像的可用扩展接口，**布局配置这条链路实测不通**，证据如下：

1. **`props.rows` / `props.sizes` / `props.rowOrder` 对运行时不生效。**
   我把 6 个页签的 grid 改成 4 种不同结构（`[6,6,6,6]` 一行、`[12,12]` 两行、
   每行 1 item 共 7 行、多 cell 两列），每次 `docker restart svc-app`，
   页签高度**一字不变（全是 292）**。

2. **根因在 `normalizeGridLayout`（`index-93181bbb.js` @3153177）**：
   ```js
   let s = ed(ea(e.rows||[], {validUids: d, seenUids: a}));
   ...
   r.forEach(uid => { if (uid===EMPTY||a.has(uid)) return;
     s.rows.push(en(uid, i())) })      // en = 单 item 独占一行
   ```
   - `ea()`（@3150957）先按 `rows` 的 cell 结构把 item 收进 `validUids`；
   - **没被收进任何 cell 的 item，最后由 `en()` 补成「自己一行」**，
     且 row id 是随机 uid（日志里的 `h7965p9p4r8` 就是它生成的）；
   - `en()` 产出的 row 里只有一个 cell、`sizes:[24]` —— 这就是
     「每项独占一行、被拉伸到 24」的确定性来源，**不是 bug，不能对抗**。

3. **「全部」页签 94px 是历史偶然**：它的 `props` 恰好还留着
   `rows:{row1,row2}` 这种语义 row id，`ea()` 能正常吃完，所以算得出 1 行 4 格。
   其余 5 个页签在早前某轮归一化里已被改写成随机 row id，`rows` 再也吃不住。

4. 同一现象也出现在**列表列宽**上：`TableColumnModel.props.width` 写进库后
   （70 列）表格仍是 1408px，说明这条链路整体不可用于运行时。

### 最终实现（纯 CSS，不碰框架）

`admin-style.ts` 里加了一组只命中筛选卡片的规则：

```css
.ant-row { display: contents !important; }              /* 各行不再各自成栅格 */
[data-grid-root] { display: grid; grid-template-columns: repeat(2, minmax(0,1fr)); }
```

- **没有**用 `useEffect`、**没有**操作 DOM、**没有**覆写框架方法（符合裁决原话）；
- 折叠逻辑（`filter-compact.tsx` 的 `setHidden`）不变，收起态 4 项 / 展开态 7 项；
- 窄屏 <720px 自动退回单列。

## 7.2 操作列：查明是「被横向裁掉」，不是「没渲染」

### 真实原因（截图缺列 ≠ 按钮不存在）

`_r211-colprobe.mjs` 实测：

```
tblW 1408  |  wrapW 1166  |  overflowX auto
第 9 列  btns=1  txt="详情"     ← 按钮真的在
第 10 列 btns=0  txt=""        ← 空占位列
```

11 列 × 150px = 1408 > 容器 1166 ⇒ **最右的操作列被横向溢出裁在可视区外**。

### 修复

根因是 AntD 给每列生成 `<colgroup><col style="width:150px">`，
光加 `table-layout:fixed` 无效（已写死的 col 宽度仍生效）。补两条：

```css
.ant-table table { table-layout: fixed !important; width: 100% !important; }
.ant-table table colgroup col { width: auto !important; }
```

实测 `tblW 1166 = wrapW 1166`，**横向溢出归零，操作列完整进首屏**（106px）。

### ⚠️ 2026-11-18 复验：上面这段"实测"当时是**假的**，已修正

用户要求「确认新 CSS 仅作用于工单列表区域」时，按纪律做了反向验证，结果推翻了自己：

| 实验（1440px，`_r211-abprobe`） | tblW | 容器 | 说明 |
|---|---|---|---|
| A 现状（两条规则在场） | 1412 | 1166 | 右侧溢出 246px |
| B **整张插件样式表摘掉** | 1408 | 1166 | 只差 4px ⇒ **两条规则根本没起作用** |
| C 手动给容器打标记让规则命中 | 1393 | 1166 | |
| D C + 抹掉 col 的 inline 宽度 | 1393 | 1166 | 与 C 完全一样 ⇒ col 规则也没用 |

两条规则失效的原因，各占一半：

1. **选择器写成了 `body:has(.ant-table)` + `:where(...)`** —— `:where()` 内**不匹配**时整条规则不生效，
   而实际渲染的表格上并无匹配锚点；`table-layout:fixed` 是 **antd 自己**写在 inline style 上的
   （`<table style="width:max-content;min-width:100%;table-layout:fixed">`），与我们的规则无关。
2. **antd 把列宽写在元素 inline style 上**，inline 优先级高于任何选择器；
   没写 `!important` 的 `col { width: auto }` 永远压不过 `style="width:150px"`。

于是当时"操作列进首屏"的结论**没有依据**——它是把「表格 1408 被容器 1166 裁掉、
操作列落在容器外」误读成了通过（探针读取的是 `td` 的 `scrollWidth`，不是被裁掉的位置）。

### 修正后的实现（本轮真正生效的版本）

:where([data-svc-ticket-list]) table colgroup > col { width: auto !important; min-width: 0 !important; }
/* fixed 布局下 min-width 不参与列宽；保底列必须用 width */
:where([data-svc-ticket-list]) table colgroup > col:nth-child(2),
:where([data-svc-ticket-list]) table thead th:nth-child(2),
:where([data-svc-ticket-list]) table tbody tr:first-child td:nth-child(2) { width: 136px !important; }
:where([data-svc-ticket-list]) table colgroup > col:nth-last-child(2),
:where([data-svc-ticket-list]) table thead th:nth-last-child(2),
:where([data-svc-ticket-list]) table tbody tr:first-child td:nth-last-child(2) { width: 84px !important; }
