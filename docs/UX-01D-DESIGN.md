## 1. 产品定位

### 1.1 一句话

> **让总部管理员在后台调整客户 H5 的"有限展示内容"，不必每次找开发改代码、重新构建、重新部署。**

### 1.2 它是什么

- 一个**带草稿、预览、发布、回滚**的**展示层配置**中心，作用于客户**报修/投诉页、成功页**，以及进度页的主题。
- 配置范围**只有四类**：品牌（名称/副标题）、主题（3 个预设）、提示文案（4 段）、非关键模块显隐（3 个开关）。
- 发布**不需要重新构建 H5**：`/h5/` 的 HTML 是 `no-store`，配置是运行期数据 ⇒ 下次打开即生效。

### 1.3 它不是什么

| 不是 | 为什么 |
|---|---|
| ❌ 通用页面构建器（拖拽 / 脚本 / 任意区块） | 会同时打破"安全边界"和"可维护性"；本工程量级撑不起一个低代码平台 |
| ❌ 任意 CSS / HTML / 外部脚本注入 | nginx **没有 CSP**（后台是低代码动态渲染，`service.conf` L153-156）⇒ 等于开门 |
| ❌ 表单字段 / 校验规则 / 隐私告知的编辑器 | 这些是**契约与法律**，不是外观 |
| ❌ 门店级"装修后台" | 15 家店 × 多参数会变成几百个孤立配置，且会与二维码归属产生危险的耦合想象 |
| ❌ UX-01C 的延伸 | 那是**业务参数**（SLA / 短信 / 门店资料）；本设计**不复用**其受管键、不混入同一张表 |

### 1.4 目标用户

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| `hq_admin`（总部管理员，1–2 人） | 改草稿、预览、发布、回滚 | —— |
| `hq_after_sales`（总部售后） | **只读**（可以看到当前线上版本与历史） | 改草稿、发布 |
| `store_*`（门店账号） | **看不到该页面**（404） | 任何装修能力 |
| 匿名客户 | 读到**已发布**配置 | 读草稿、读历史 |

> 依据：UX-01C 已确立"总部配置只有 `hq_admin` 能写、其它角色 403"的口径（`config-settings.ts` / `store-profile.ts` 门禁）。
> UX-01D 沿用同一口径，**不新开一套权限语义**。

## 2. 明确不做（第一期红线）

| # | 不做 | 理由 |
|---|---|---|
| N1 | 门店级覆盖 | 见 §3.5 / §11-D1；进度页拿不到门店入口（AUDIT G12），做了必然出现"同店两页不一致" |

| N8 | 定时发布 / A-B 测试 / 多语言 | 第一期无必要；A-B 还会让客诉无法复现 |

### 3.2 A 基础品牌

**为什么平台名要做成可配置**：现在它写死在 `Report/index.vue` L6 与 `index.html` L15 两处，
换品牌/换运营主体必须改代码 + 重新构建 + 部署。这是"找开发改代码"最典型的一处。

**必须同时处理两处**（AUDIT G4）：
- 页头 `h1` → 渲染配置值；
- 浏览器页签 → 运行时 `document.title = \`${name} · 服务报修\``；`index.html` 里的静态值只作**兜底**（JS 未执行时）。

**副标题**：今天**根本没有这个位置**。`.svc-header p` 的样式已存在（`base.css` L67-71），
所以新增一行**不需要新样式**，只是把已有样式用起来。默认空 ⇒ 不渲染。

### 3.3 B 页面主题

**技术前提已具备**：`base.css` 的 `:root` 只有 12 个变量，组件里几乎没有散落的主色硬编码
（唯一例外是进度页徽标，见 AUDIT B-20，属缺陷不属主题）。

**三个预设**（第一期就三个，不做自定义）：

| 预设 | `--svc-primary` | 白字对比度 | `--svc-primary-weak` | 适用 |
|---|---|---|---|---|
| `classic-blue`（默认，= 今天的样子） | `#2f6fed` | **4.55:1** ✅ | `#eaf1ff` | 中性、通用 |
| `brand-red` | `#c8362c` | **5.22:1** ✅ | `#fdecea` | 家电连锁常见主色 |
| `graphite` | `#475569` | **7.58:1** ✅ | `#eef1f5` | 极简、低饱和 |

> 对比度为**实测计算**（WCAG 相对亮度公式），不是目测。
> ⚠️ 现状 `--svc-text-weak: #8a9099` 只有 **3.22:1**（白底），不达标（AUDIT B-23）——
> 每个预设必须同时定义达标的 `--svc-text-weak`（建议 `#5f6670`，5.80:1 / 页面底 5.36:1）。

**深色模式**：现有 `@media (prefers-color-scheme: dark)` 只覆盖了 6 个变量，
**`--svc-primary` 没有深色值**（AUDIT §3.5）。⇒ 每个预设必须给 `primary` 一个**浅化版**（如蓝 `#7ea6ff`），
否则深色下"亮蓝按钮 + 深底"刺眼且对比不稳。

**按钮外观 `soft` 的现实约束**（实测）：`#2f6fed` 放在 `#eaf1ff` 上只有 **4.01:1**，
17px/600 的按钮文字**不算大字号**（AA 大字号门槛是 24px 或 18.66px 粗体）⇒ **soft + 蓝不达标**。
⇒ 若保留 `soft`，两种选择：① 文字改用更深的同色（蓝系 `#1d4ed8`，6.70:1）；
② 第一期**只做 `solid`**，`soft` 延后。**本设计推荐 ②**（少一个组合就少一类对比度事故）。

### 3.4 C 页面文案

**四段可编辑文案，位置都是"新增的空位"或"已有的一句提示"**，不动任何字段标签。逐段说明边界：

| 项 | 允许写什么 | 不允许写什么（服务端会拒） | 为什么 |
|---|---|---|---|
| C1 报修引导 | 流程说明（"拍照说明故障，师傅会先电话联系"）、服务范围 | 时限承诺（"2 小时上门"）、价格、保修期、绝对化用语 | 这些是**业务承诺**，应由 SLA 配置与门店口径决定，不该由装修页悄悄改 |
| C2 投诉引导 | 投诉受理说明、希望客户提供的信息 | "一定赔偿/一定处理"等结果承诺 | 同上 |
| C3 媒体帮助 | 换一种说法表达"文字与媒体任选其一" | 任何改变**提交规则**的说法（"必须上传照片"） | 规则由服务端定，文案不能与之矛盾 |
| C4 成功说明 | "门店会尽快联系您"、保存单号提示 | "已受理""师傅已派工"等**与状态机冲突**的话 | 刚建单的状态是 `NEW`＝"已提交"（`Success.vue` L11-21 已明确此口径） |

**校验只做"形态"不做"语义"**：长度、字符、单行、禁 `<` `>` 可实现；
"是否构成承诺"无法机器判定 ⇒ 用**明确的字段说明 + 发布前 diff 确认**来兜（§8.3），
并在文案说明里写清"这里写的话客户会当真"。

### 3.5 D 展示模块

只允许三个**低风险**开关。**没有"模块排序"**：现有页面除选填区外没有可重排的模块，
为排序而排序会诱导把"字段"也搬来搬去（那是契约）。

**明确不允许隐藏的模块**（哪怕管理员想）：门店信息卡、报修/投诉切换、表单字段、媒体入口、
提交按钮、隐私页脚、进度页时间线。

### 3.6 E 门店差异化（**只提方案，不自行决定**）

#### 方案对比

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| **S0（推荐）总部统一** | 只有一套配置，全部门店一致 | 最简单；无一致性裂缝；`progress` 页不冲突 | 无法满足"某店想突出自己品牌" |
| S1 门店覆盖（全字段） | 门店可选覆盖任意字段，未覆盖继承总部 | 灵活 | 15 店 × 12 项 = 最多 180 份配置；进度页无入口 ⇒ **同店两页不同主题**；审计与回滚复杂度翻倍 |
| S2 门店覆盖（仅 4 项） | 只允许覆盖 `brand.subtitle` + `copy.report_intro` + `copy.complaint_intro` + `theme.preset`，其余强制继承 | 风险可控 | 仍解决不了进度页（G12）；且"红色门店 + 蓝色进度页"的观感问题依旧 |
| S3 门店覆盖 + 进度页带 scope | 进度 Token 里附带**不透明**的 scope 标识（不是门店 code） | 一致性可解 | 要改进度 Token 的签发/校验（安全面）；属于 P11-4 的改动，**跨阶段** |

#### 推荐

**第一期选 S0。** 理由按重要性排序：

1. **进度页没有门店入口**（G12）⇒ 任何门店级外观都会在两页之间产生裂缝，而客户是**连着看**的；
2. 门店账号的角色定位是"处理工单"，不是"经营品牌"；15 家店各自装修会产生**无法集中治理**的视觉漂移；
3. S3 需要动**进度 Token 的签发**（安全边界），不应被"装修"这个需求顺带推动；
4. 若将来确有需求，S2 是安全的第一步 —— 但**必须先解决 G12**，再谈覆盖。

#### 无论选哪个方案都不可逾越的红线

> **门店级外观配置，永远不得影响"这单属于哪家门店"。**
> 归属只由 `resolveStoreEntry()`（HMAC 签名入口）决定；装修配置**不参与**、**不得携带**、**不得改写** `k`。
> 门店资料（名称/电话/地址）来自 `stores` 表，属"资料"不属"外观"，门店可改；但**改资料也不改归属**。

## 4. 受保护区域（冻结清单）

| # | 受保护区 | 允许的视觉优化 | **绝不允许** |
|---|---|---|---|
| P1 | 联系人与手机号字段 | 字号、间距、边框 | 改标签、改必填、改校验、改字段名 |
| P2 | 报修/投诉业务类型 | 切换条的配色/高度 | 合并、改名、加第三个类型 |
| P3 | 服务端字段校验规则 | —— | 前端放宽/收紧（前端只是"少发必然被拒的请求"） |
| P4 | 照片/录音/视频上传能力 | 卡片配色、图标尺寸 | 关闭入口、改采集方式、改限额语义 |
| P5 | "文字或有效媒体至少一种"提交规则 | 提示文案 | 改成"必须文字"或"必须媒体" |
| P6 | 隐私告知与授权机制 | 字号、对比度 | 删告知、默认勾选、改用途描述 |
| P7 | 工单状态与后台处理流程 | 进度页徽标样式（修 B-20） | 改状态文案含义（"待处理"≠"已受理"） |
| P8 | 门店签名二维码与归属校验 | 二维码图片样式（后台） | 改签名、改归属、门店级外观影响归属 |
| P9 | 进度 Token、有效期、访问权限 | 过期提示的**排版** | 改有效期、去掉鉴权、把 Token 写进日志/Referer |
| P10 | 固定提交按钮的可用性与安全区 | 颜色、圆角、字号 | 改高度 <44px、去掉 `env(safe-area-inset-bottom)`、去掉防连点 |
| P11 | 客服资料与工单真实关联 | —— | 用装修数据覆盖/伪造门店身份 |
| P12 | 法律与对客承诺文案（5 处） | 排版 | 编辑内容（见 §3.4 末） |

**判定方法（给实施阶段用）**：任何新配置项，只要**能改变**上述任一行的"存在性/语义/校验/安全边界"，
就不属于 UX-01D。

## 5. 页面布局方案

> 以下是**设计草案**（文本线框），不是已实现的页面。真实基线截图见 `.tmp-verify/ux01d/`。
> 标注 `[配置]` 的才是可装修项，其余是冻结结构。

### 5.1 客户报修页（375 宽）

```
┌───────────────────────────────────────┐
│ 四川七方连锁售后服务平台        ← [A1] 18px/600，单行
│ 服务预约 · 快速报修            ← [A2] 13px，默认不显示
```

## 6. 预览 / 发布 / 回滚契约（核心）

### 6.1 三态模型

| 状态 | 存在哪 | 谁能看 | 客户能看到吗 |
|---|---|---|---|
| **默认**（从未发布） | 代码里的 `DEFAULT_UI` | 所有人（H5 内置兜底） | 是（= 今天的页面） |
| **草稿** | `page_theme_drafts.doc`（每 scope 一行，`revision` 递增） | `hq_admin`（后台 / 预览凭证） | **否** |
| **已发布** | `page_theme_releases`（不可变，`version` 递增） | 所有人（公开接口只读最新版） | 是 |

### 6.2 数据流

```
                    ┌──────────── 后台（hq_admin） ────────────┐
 编辑 ──► 保存草稿 ──┤ svc:uiThemeSave（revision 乐观锁）        │
                    │ svc:uiThemePreview（10 分钟凭证）         │
                    └───────────────┬─────────────────────────┘
                                    │ iframe（URL 里**没有**凭证）
                                    ▼
                     /h5/report?uiPreview=1
                                    │  postMessage（同源）
                                    ▼
             后台先调 svc:uiThemePreviewDoc 消费凭证（登录+hq_admin+签发者本人）
                                    │
                    只把【doc】postMessage 给 iframe（凭证不进入 H5）
                                    │
                          预览模式：不可提交、不拉门店、无媒体

                    ┌──────────── 发布 ────────────┐
 点发布 ──► 确认 diff ──► svc:uiThemePublish ──► 事务内插入 release（version+1）
                    └───────────────┬──────────────┘
                                    ▼
        客户下次打开 ──► GET /api/public/ui-config?k=… ──► 返回【最新 release】
                                    │
                          ETag: W/"hq-12" + Cache-Control: no-cache
```

### 6.3 用户 §六 的 10 个问题，逐条回答

| # | 问题 | 答案 |
|---|---|---|
| 1 | 草稿与已发布如何区分 | **两张表**：草稿可覆盖更新（带 `revision`），发布版本不可变（只追加）。后台顶部常驻"草稿 vN / 线上 vN" |
| 2 | 改草稿会不会影响真实客户 | **不会**。公开接口只读 `page_theme_releases` 的最新一行；草稿只能经短时预览凭证读取。门禁会断言"保存草稿后公开接口返回值不变" |
| 3 | 预览用什么安全入口 | 三层同时成立才看得到草稿：① **`hq_admin` 有效登录**（mint 时就要求，签发时记录签发者）；② **短时签名凭证**（HMAC，10 分钟，绑定 `签发者 + 草稿 revision`，**不落库**）；③ **revision 仍是最新** —— 草稿被改过后旧凭证返回 **409 `PREVIEW_STALE`**，绝不"静默显示另一份草稿"。<br>凭证怎么送到内容面：iframe 的 URL 里**不含凭证**（`?uiPreview=1`）；凭证由**后台**用受控动作 `svc:uiThemePreviewDoc` 消费（登录 + hq_admin + 签发者本人 + revision 未变），再把 **doc** 通过同源 `postMessage` 交给页面。<br>⇒ 凭证**从不进入 H5（匿名）上下文**，也不出现在 URL / access log / `Referer`。过期/篡改 ⇒ 401；revision 变 ⇒ 409，页面提示"草稿已更新，请在后台重新打开" |
| 4 | 报修与投诉预览如何切换 | 预览页与真实页**同一个组件**，切 tab 即可；也支持 `&mode=complaint` 直接打开投诉态。两态共用同一份配置 |
| 5 | 三视口怎么检查 | 后台预览面板提供 **375 / 390 / 420** 三档 iframe（按 CSS px 设宽，DPR 由设备决定）；同一屏内并排或切换；**不缩放**（缩放会掩盖折行问题）。真机验证仍需真机（本轮无真机，不宣称通过） |
| 6 | 发布后 H5 怎样读取对应版本 | 页面启动 `fetchUiConfig(entry)` → 接口返回 `{version, brand, theme, copy, modules}` → 应用到 CSS 变量与文案。**不缓存到 localStorage/sessionStorage**（否则发布后要等缓存过期） |
| 7 | 浏览器缓存如何同步 | `/h5/` HTML 已 `no-store`（nginx L217）⇒ 配置不会随 HTML 被缓存；配置接口用 `Cache-Control: no-cache` + `ETag: W/"hq-<version>"`，未变时 304（省流量），发布后 ETag 变了 ⇒ 下次打开立即生效。**H5 资源不需要重新构建**（assets 是代码哈希，与配置无关） |
| 8 | 发布失败如何恢复 | 发布是**单事务**：校验 → 计算 `version+1` → 插入 release → **条件更新草稿（`base_version` 且 `revision+1`，WHERE 带旧 revision）**。任一步失败 ⇒ 回滚，**线上不变**，草稿保留，返回 409（并发）/422（校验）/500（数据库），后台提示"发布失败，线上仍是 vN"。<br>⚠️ **必须推进 revision**：否则同一版草稿可被连续发布两次（v11、v12 都 200），见 DEV-210 |
| 9 | 如何回滚上一版 | `svc:uiThemeRollback { to_version }` ⇒ **以该版本快照再发一版**（`version+1`，`rolled_back_from=to_version`），并把草稿内容同步为该快照（`revision+1`）。**不删除、不改写历史** |
| 10 | 如何记录发布者、时间与变更 | `page_theme_releases` 每行自带 `published_by / published_at / version / note / rolled_back_from`；`doc` 是完整快照 ⇒ 任意两版可做字段级 diff。后台展示最近 20 条，可查看 diff |

### 6.4 同源 iframe 可行性（已核实，不是假设）

nginx 对 H5 设置了 `X-Frame-Options: SAMEORIGIN`（`nginx/conf.d/service.conf` L156）
⇒ **后台（同源 `/admin`）用 iframe 嵌 `/h5/report?uiPreview=1` 是允许的**；
外部站点嵌入会被浏览器拒绝 —— 这正是我们想要的方向（预览只给后台用，不做可分享链接）。

同源还带来一个必要条件：`postMessage` 的 `event.origin` 必须等于 `location.origin`，
且 `event.source === window.parent` —— 两者都校验，避免把凭证交给未知窗口。

### 6.5 预览的"零副作用"是怎么保证的

| 副作用 | 保证方式 |
|---|---|
| 建工单 | 预览页**不加载真实入口**：`store-entry` 根本不调用；提交按钮渲染为禁用态；即便有人手工构造请求，`entry` 是预览占位串 ⇒ 服务端 `resolveStoreEntry` 直接 404 |
| 发短信 | 无建单 ⇒ 无 `PROGRESS_LINK` 短信；预览接口本身不写库 |
| 上传媒体 | 四个媒体入口在预览态禁用；`createMediaSession` 不被调用 |
| 读真实门店数据 | 预览返回**合成门店**（`示例门店` / `0833-0000000` / `示例地址`），不查 `stores` |
| 泄漏草稿 | 凭证绑定 `签发者 + revision` 且 10 分钟过期；消费端还要**登录 + hq_admin + 签发者本人**；不带凭证 / 篡改 / 过期一律 401；revision 变过 ⇒ 409（不显示任何草稿） |
| 凭证外泄到日志 | 凭证只在后台内存里传给 `svc:uiThemePreviewDoc`（POST body）；iframe 只收 `doc`；URL / `Referer` / nginx access log 里都不出现 |

## 7. 数据模型（推荐：独立模型）

### 7.1 为什么**不**复用 `serviceSettings`

| # | 原因 | 具体 |
|---|---|---|
| 1 | **没有版本维度** | `serviceSettings` 是"一键一值"，发布是**整份快照切换**；用 12 个键就要发 12 次，中间任何一次失败 ⇒ 客户看到"新主题 + 旧文案"的混合态 |
| 2 | **不是单值** | 主题/文案/模块是**结构化文档**（含 schema_version、嵌套分组），塞进字符串列只能整段 JSON 硬编码，等于把结构校验丢掉 |
| 3 | **审计粒度不对** | `configChangeAudits` 是"键 → old/new"，适合标量；12 个键会产生 12 条互不关联的审计，**看不出"这是一次发布"** |
| 4 | **并发语义不同** | 现有并发控制是 `expected_value`（比较值）；装修需要的是 `expected_revision`（比较整份草稿的第几次修改） |
| 5 | **用户明令禁止** | 不得复用受管 SLA/SMS 键；也不应把展示配置混进同一张"业务参数"表，否则 UX-01C 的"只回 SLA 三键"收窄会被破坏 |

### 7.2 表结构

```sql
-- 草稿：每 scope 一行（v1 只有 'hq'）
page_theme_drafts
  id            bigserial primary key
  scope         varchar(16) not null default 'hq'
  revision      int not null default 1          -- 每次保存 +1
  base_version  int not null default 0          -- 基于哪个已发布版本
  doc           jsonb not null                  -- 通过 schema 校验的完整文档
  updated_by    bigint                          -- 操作人 user id
  request_id    uuid                            -- 幂等键（唯一）
  created_at    timestamptz not null default now()
  updated_at    timestamptz not null default now()
  UNIQUE (scope)
  UNIQUE (request_id)

-- 发布版本：不可变，只追加
page_theme_releases
  id                bigserial primary key
  scope             varchar(16) not null
  version           int not null
  doc               jsonb not null              -- 完整快照（含 schema_version）
  published_by      bigint
  published_at      timestamptz not null default now()
  note              varchar(200)                -- 发布说明（"换主题"）
  rolled_back_from  int                         -- 回滚来源版本（普通发布为 null）
  request_id        uuid                        -- 幂等键（唯一）
  UNIQUE (scope, version)
  UNIQUE (request_id)
  INDEX (scope, version DESC)
```

> 索引要与 `scripts/expected-indexes.mjs` 同步登记（这是本项目"建了索引必须有门禁认领"的纪律）。

### 7.3 发布事务与版本分配

```
BEGIN
  SELECT * FROM page_theme_drafts WHERE scope='hq' FOR UPDATE;   -- 行锁
  -- 校验提交上来的 expected_revision 与库中 revision 一致
  -- 校验 doc（schema/长度/枚举/字符）
  SELECT COALESCE(MAX(version),0)+1 AS next FROM page_theme_releases WHERE scope='hq';
  INSERT INTO page_theme_releases(scope, version, doc, published_by, note, request_id) ...;
  -- 🔴 条件更新：revision 必须进 WHERE；影响行数≠1 ⇒ 409（并发发布的最后一道闸）
  UPDATE page_theme_drafts
     SET base_version = next, revision = revision + 1
   WHERE scope='hq' AND revision = <进入事务时读到的 revision>;
COMMIT
```

- 并发：两个管理员同时点发布，第二个在行锁上等待，读到 `revision` 已变 ⇒ **409**（不产生重复版本）。
- 兜底：`UNIQUE(scope, version)` 防多实例下的竞态（撞 23505 ⇒ 重试一次或返回 409）。
- 幂等：同一 `request_id` + **内容相同**的重放 ⇒ 直接返回上次的 `{version}`，**不再插入**；
  同一 `request_id` + **内容不同** ⇒ **409 `IDEMPOTENT_PAYLOAD_MISMATCH`**（复用一个请求号干两件事，必须拒绝）。

### 7.4 公开读取与缓存

```
GET /api/public/ui-config?k=<门店入口，可省略>
200 {
  "version": 12,
  "schema_version": 1,
  "brand":   { "name": "...", "subtitle": "...", "logo": "none" },
  "theme":   { "preset": "classic-blue", "button": "solid", "card": "bordered" },
  "copy":    { "report_intro": "", "complaint_intro": "", "media_help": "...", "success_note": "" },
  "modules": { "media_help": true, "extra_open": false, "success_copy_no": true }
}
ETag: W/"hq-12"
Cache-Control: no-cache
```

- **只回白名单字段**，不回内部 id / 门店 code / 操作人（沿用 `store.ts` 的最小投影纪律）。
- `k` 只用于**将来**的门店覆盖解析；v1 无论有没有 `k` 都返回 `hq` 的版本（**不得**因此改变归属判定）。
- 限流：用**独立场景**（不占 `store-entry` 的 30/min 桶，否则一个页面要打两次入口桶）。
- 配置不存在/读取失败 ⇒ H5 **静默用内置默认值**，绝不白屏（门禁会断"接口 500 时页面仍可用"）。

### 7.5 schema 演进

- `doc.schema_version` 整数；读取端按版本兼容（未知键忽略、缺失键补默认）。
- 新增字段：老版本快照缺该键 ⇒ 用默认值补，**不迁移历史行**（快照不可变）。
- 删除字段：先停止读，再在两个发布周期后清理（不得直接删快照里的键）。

## 8. 后台信息架构与操作流程

### 8.1 页面与导航

### 8.2 六个动作与权限

| 动作 | 作用 | `hq_admin` | `hq_after_sales` | `store_*` | `viewer` | 匿名 |
|---|---|---|---|---|---|---|
| `svc:uiThemeDraft` | 读草稿 + 当前线上版本 | ✅ | 403 | 403 | 403 | 401 |
| `svc:uiThemeSave` | 保存草稿（`expected_revision`） | ✅ | 403 | 403 | 403 | 401 |
| `svc:uiThemePreview` | 签发预览凭证（10 分钟） | ✅ | 403 | 403 | 403 | 401 |

写只走 `svc:*`，读也只走 `svc:*` —— 否则"绕过发布审核直接改表"就变成了合法路径。

### 8.3 让非技术人员不出错的设计

| 机制 | 具体 |
|---|---|
| 每个字段三段说明 | 中文名 + "显示在哪里" + "长度/默认值" |
| 默认值可见 | 输入框 placeholder 就是默认值；旁注「留空 = 用默认」 |
| 恢复默认 | 按字段 + 整页两级；整页需二次确认 |
| 状态永远可见 | 顶部「草稿 v4（3 项未发布）· 线上 v3（时间）」 |
| 未保存提醒 | 有改动时离开页面弹确认 |
| 发布前 diff | 只列**变更项**（3 条），不列 12 项 |
| 发布后回执 | 「已发布 v4，客户下次打开即生效」+ 直达预览 |
| 失败可读 | 422 说清哪个字段、409 说"别人刚改过，请刷新" |

## 10. 真实验收标准（可断言，不是"看起来行"）

| # | 标准 | 判据 | 归属门禁 |
|---|---|---|---|
| 1 | **默认值等价** | 未发布时，公开接口返回的 `doc` 与 H5 内置默认**逐字段相等**；页面文案与今天**逐字节相同**（截图/文本双比对） | `-config` |
| 2 | **白名单** | 提交含未知键 ⇒ 422；`schema_version` 不支持 ⇒ 422 | `-config` |
| 3 | **文本安全** | 含 `<` `>`/控制字符/换行 ⇒ 422；渲染后 `document.body.innerText` 出现原文而 DOM 中**无新增元素**（证明按文本渲染） | `-config` + `-h5` |
| 4 | **并发** | 两个会话同 `expected_revision` 保存 ⇒ 200 + 409；只多一条 revision | `-publish` |
| 5 | **幂等** | 同 `request_id` 重复发布 ⇒ 返回同一 `version`，release 表**只增 1 行** | `-publish` |
| 6 | **发布原子** | 注入校验失败/DB 错误 ⇒ 线上 `version` 不变、草稿不变、无半行 | `-publish` |
| 7 | **草稿隔离** | 保存草稿后，匿名 `ui-config` 的 `version` 与内容**均不变** | `-publish` |
| 8 | **回滚** | 回滚到 v2 ⇒ 新版本 v4 的 `doc` **逐字段等于** v2，`rolled_back_from=2`，v2/v3 仍在 | `-publish` |
| 9 | **预览零副作用** | 预览页：`tickets` 计数不变、`sms_logs` 不变、`customer_media_sessions` 不变；提交按钮 `disabled`；Token 过期 ⇒ 401 | `-publish` + `-h5` |
| 10 | **三视口** | 375/390/420 下 `document.documentElement.scrollWidth <= innerWidth`（无横向滚动）；关键区块 `getBoundingClientRect().width > 0` | `-h5` |
| 11 | **对比度** | 每个预设：主按钮白字 ≥4.5（或 ≥3 且字号 ≥24px/18.66px 粗）、正文 ≥4.5、次要文字 ≥4.5 | `-config`（token 表断言） |
| 12 | **触控** | 所有可点元素高度/宽度 ≥44px（含媒体卡片、tab、按钮） | `-h5` |
| 13 | **缓存** | 发布前后 `ETag` 必变；未发布时重复请求返回 304 且内容一致 | `-publish` |
| 14 | **冻结回归** | `settings-auth 29/0`、`store-entry 36/0`、`pages 26/0`、`ux-media-01 58/0`、`store-profile 71/0` 保持全绿 | 既有门禁 |

> **反向验证要求**（本项目铁律）：每条断言都要证明"**它真的会红**"——
> 至少对 3 条关键断言（草稿隔离、回滚一致、预览零副作用）做变异测试（故意破坏实现 ⇒ 必须红 ⇒ 还原 ⇒ 复绿）。
