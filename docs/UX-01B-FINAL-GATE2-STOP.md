## 2. 卡在哪（§八 停止条件命中）

### 2.1 插件在新库未启用

```
GET http://127.0.0.1:13001/api/public/store-entry?k=S01.xxx
→ 404  Not Found（纯文本，非 JSON）
```

对照原实例同一个 token：

```
GET https://127.0.0.1/api/public/store-entry?k=S01.xxx
→ 200 {"data":{"code":"S01","name":"新都圣大家电",...}}
```

**原因**：`@local/service-ticket` 的**源码**靠 bind mount 挂进了 `node_modules`，但**插件启用状态在新库里是空的**（NocoBase 的插件注册写在数据库）。新库只跑了框架 migration，没跑过插件的 enable/upgrade。

### 2.2 H5 仍连原实例

H5 的请求路径是**相对** `/api/...`（`h5/src/api/http.ts`），经 nginx 落到 **`svc-app`（原实例）**。

要让 H5 打到 13001，目前只有三条路：

| 路径 | 代价 | 风险 |
|---|---|---|
| A. 改 nginx 加一条 `/uat-api → 13001` | 改 `nginx.conf` + reload | **可能影响现有路由**（用户明确"不得干扰现有服务"） |
| B. 改 H5 的 baseURL | 改 H5 源码 | **违反"不改产品代码"**，且要重新构建 |
| C. CDP `Fetch` 拦截 `/api/*` 转发到 13001 | 只改测试脚本 | 不改任何配置/代码；但需要在拦截层处理 CORS 与响应体，且 `store-entry` 得先能通（现在 404） |

**我先试的是 C 的前提**——结果发现新实例本身就没启用插件，所以 C 也走不通。

**按 §八「UAT H5 仍连接原有业务数据库 ⇒ 立即停止并报告」——我停在这里。**

## 5. 我的判断

**"真正隔离的 UAT 实例"不是起一个空 NocoBase 就能用的**——它需要：插件启用 + 账号 + 页面 seed + 门店身份配置 + H5 路由转发。这四件里，**有两件（插件启用、页面 seed）会动到"部署形态"**，已经超出"UI 精修验收"的范围。

**两条可选路线，请你选**：

**路线 1（真隔离，成本高）**
继续把 UAT 实例搭完（插件启用 + seed + H5 转发）。预计还要若干轮，且要接受"为验收搭一套双实例环境"的维护成本。

**路线 2（在现有实例上做，靠 run-id + 精确清理兜底）**
- 仍在**原实例**建 2 张工单，但：
  - 客户名强制带 `run-id`（如 `合成UX01B42-甲`）
  - 门店 S01（drill 范围）
  - 建完立刻用 `purge-ux01b-ticket.mjs` 逐张清理
- **风险**：建单确实写进了含 489 张真实工单的库（虽然只增 2 张、且能精确删）
- **这是 Gate 1 预检时我判断"可以但有条件"的那条路**，你当时选择了"必须真隔离"

**我不替你选。** 但我要说清楚：路线 2 的风险是**短暂的 2 条真实写入**，路线 1 的成本是**一整套双实例运维**。
