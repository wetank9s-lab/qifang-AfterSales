## 四、未决问题（**当前阻塞，已排障到这一步**）

**现象**：`GET /api/technician/visits/<token>/media/<ref>` 一律返回
`401 {"code":"INVALID_TOKEN","message":"Your session has expired. Please sign in again."}`

**已排除的**（都有证据）：

1. **Token 无效** —— 排除。**同一个 Token** 请求 `:get` 返回 200；
2. **nginx 重写没生效** —— 排除。ref 形态非法（长度不对）时得到的是**应用层 404**
   （说明重写对合法形态会生效；非法形态按设计不重写）；
3. **我的 handler 鉴权失败** —— **基本排除**。在 `media` handler 里临时加过一条
   "只打印长度、不打印内容"的诊断日志，跑完整轮验收后**日志一条都没有**
   ⇒ 请求**根本没进到这个 handler**；
4. **媒体没绑定到工单** —— 排除。库里三张单各有 1 份媒体（image/audio/video）；
5. **字段名取错** —— 已修（`listForTicket` 输出是 camelCase 的 `kind`/`durationMs`，
   第一版按数据库列名取 ⇒ `kind` 恒空、时长 null，**已修正并验证通过**）。

**因此 401 来自 handler 之前的 ACL 中间件**。下一步应该查的两处：

1. **在 `_auth.ts` 的 `authenticateTechnician()` 入口加同款诊断**（比 handler 更前一步）：
   若它也**没有输出** ⇒ 确认是 NocoBase 的 ACL 中间件在拦；若有输出 ⇒ 在 `param(ctx,'token')` 取参。
2. **对比 `technicianVisit:photo` 是怎么被放行的**（它能用）：
   两者在形状表里同级、都用同一个 `authed()` 包装 ⇒ 差异只可能在
   「ACL 对**新 action** 的登记」（例如需要在 ACL 初始化/迁移里登记，而不只是 `resourcer.define`）。

## 七、打通记录（本轮后续补充）

### 7.1 真因：**新增匿名 action 必须同时改三处**，我漏了第一处

`401 INVALID_TOKEN` 的根因是 **ACL 没放行** —— 项目的匿名资源有**三张必须同步的表**：

| # | 位置 | 作用 | 漏掉的后果（实测） |
|---|---|---|---|
| ① | `constants.ts` 的 **`ANONYMOUS_ACTIONS`** | `acl.allow(resource, action)` 的逐条放行清单 | 🔴 **401/403：接口存在却永远调不通**（本轮踩到的就是这个） |
| ② | `plugin.ts` 的 `ANONYMOUS_RESOURCE_SHAPES` | 资源上真正**注册**该 action | 启动期自检**直接拒绝启动**（日志：`handler 未进形状表（将永远不可达）`） |
| ③ | `scripts/verify-plugin-load.mjs` 的匿名白名单期望 | 门禁 | 门禁红，并**精确指出**运行时白名单缺哪一条 |

⇒ ①漏了 ⇒ 门禁把运行时白名单原样打出来，与期望一比对就锁定了缺项 ✓
（这正是"**断言要落到精确枚举**"的价值：只看数量或只看 HTTP 码都指向不了这里。）

## 八、权限边界专项验证（2026-10-14 补充）—— **15/15 通过**

脚本：`scripts/verify-technician-media-revoke.mjs`（**不改产品限流、不伪造 IP**）

### 8.1 为什么单独做这一遍

既有的端到端脚本请求密度高，容易撞 `svc_public`（`rate=30r/m`、`burst=10`，键是**客户端 IP**）。
权限类断言**必须**是明确的 401/403/404 —— **429 既不能算通过也不能算失败**。
⇒ 本脚本只做权限，节奏放慢（2.5s/请求），遇 429 等一个完整窗口再重试。
⇒ 全程**没有**修改 nginx 的 rate/burst（那是对客额度，不是测试旋钮），
  也**没有**伪造 `X-Forwarded-For`（那会绕过"按客户端 IP 限流"这条安全规则）。

### 8.2 判据与结果

| # | 判据 | 实测 |
|---|---|---|
| ① | 派工有效 ⇒ 本单客户媒体可访问 | ✅ 200 且字节与样本一致 |
| ① | **前置自检**：撤销已写入库（`token_revoked_at` 非空） | ✅ 命中 1 行 |
| ② | 撤销派工 ⇒ **详情**明确拒绝 | ✅ **401 `TOKEN_INVALID`** |
| ② | 撤销派工 ⇒ **媒体**明确拒绝（**不是 429**） | ✅ **401 `TOKEN_INVALID`** |
| ③ | 改派给另一位师傅（既有 `svc:reassign`） | ✅ 200；旧 visit 置 `SUPERSEDED` |
| ③ | **旧师傅链接** ⇒ 详情拒绝 | ✅ 401 |
| ③ | **旧师傅链接 + 原 ref** ⇒ 媒体拒绝 | ✅ 401 |
| ③ | **新师傅**：可读新授权范围 | ✅ 200 且字节一致 |
| ③ | 🔴 **新师傅的链接 + 旧句柄 ⇒ 404** | ✅ `MEDIA_NOT_FOUND` |
| ③ | 🔴 **新链接 + 旧 ref ⇒ 404** | ✅ **`ref` 不能替代服务端对当前派工的授权检查** |
| ④ | 跨工单 ref ⇒ 404 | ✅ |
| ④ | 篡改 ref ⇒ 404 | ✅ |
| ④ | 伪造 Token ⇒ 401 | ✅ |

⇒ **结论**：`ref` 只是句柄，**授权最终由服务端按「当前派工是否有效 / 是否被撤销或取代 /
媒体是否属于本工单」判定**；换链接、换 ref、伪造参数都过不去。

### 8.3 一个重要教训（**差一点误报产品缺陷**）

第一次跑时："撤销后详情与媒体**仍返回 200**" —— 看起来是**严重的安全缺陷**。

**真相是我的测试脚本坏了**：我用 SQL 的 `digest(token, 'sha256')` 去匹配 `access_token_hash`，
而**本库没装 `pgcrypto`** ⇒ 函数不存在 ⇒ 但 `psqlExec` **把这条错误吞掉了**
⇒ UPDATE **静默不生效** ⇒ 撤销根本没写入 ⇒ 接口当然正常。

⇒ 是**前置自检断言**（"撤销已写入库"）把真相逼出来的。

⇒ **教训**：凡是"通过改数据来验证行为"的测试，**必须同时断言数据真的被改了**；
   否则"改数据失败"会伪装成"产品没按预期拒绝" —— 而这两者的处置方式完全相反。
   （本项目已有同族记录：DEV-188/196 的"脚本搬家忘改路径"、DEV-199 的"断言太宽"。）
