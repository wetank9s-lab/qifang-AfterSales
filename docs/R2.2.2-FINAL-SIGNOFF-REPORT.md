## 二、返回按钮微调 ✅

**真凶不是我们的 CSS**。`Konsta Navbar.js:190` 无条件用 `<Glass>` 包住左侧：

```jsx
left && <Glass className={c.left}>{left}</Glass>
```

`Glass` 在 iOS 下恒加四个类，实测包裹层是 **44×44**：

| 类 | 计算值 |
|---|---|
| `rounded-full` | `border-radius: 3.35544e+07px` |
| `bg-ios-light-glass` | `rgba(255,255,255,0.75)` |
| `shadow-ios-light-glass` | inset 黑白多层 |
| `backdrop-blur-lg` | 毛玻璃 |

**修法**：用 Konsta 留出的 `leftClassName` 口子（`cls(leftClassName || leftClass)`）
抹平这四项 —— `bg-transparent shadow-none backdrop-blur-0 rounded-none`。
**只改 `PageHeader` 这一个组件，不做全局 CSS 覆盖**（用户明令）。

同时把图标换成自绘细线条 chevron（`stroke-width: 2` / 品牌色 `#0062CC`），
因为 Konsta 的 `BackIcon` 是 `fill: currentColor` 的**实心块**，不是 iOS 的细箭头。

⚠️ 第一次改完出现**两个箭头**：`NavbarBackLink` 结构是
`[<span>{内置 BackIcon}</span>, ...children]`，内置图标没有任何 prop 能关。
判据从"看起来对不对"改成"可见 svg 个数 == 1"，再用
`[&>span:first-child]:hidden` 精确藏掉那**一个**内置图标。

| 判据 | 结果 |
|---|---|
| 包裹层背景 | `rgba(0,0,0,0)` |
| 包裹层圆角 | `0px` |
| 包裹层阴影 | 全分量 `rgba(0,0,0,0)`（视觉无阴影） |
| `backdrop-filter` | `none` |
| 点击区 | **44×44** @(16,16) |
| 可见箭头个数 | **1** |
| 图标形态 | `fill=none` / `strokeWidth=2px` / `testid=qf-back-chevron` |
| 点击后路由 | `/m/archives/395` → `/m/archives` ✅ |

返回路由与 `handleBack` 逻辑一个字没改。

## 三、已完成阶段 0/6 照片核查 ✅ 结论：历史演示数据，**不是业务缺陷**

### 用户要求核实的四点

**① 是否历史演示数据直接写入造成？** —— **是。**

`DEMO-R2221-B`（id=395）档案级元信息：

```

customer_mobile = 13900001200
service_address = 演示路 2 号（隔离测试数据）
created_at   = updated_at = 2026-11-19 15:34:24.779211+08
```

`created_at == updated_at` 且六阶段 `completed_at` 间隔精确为 5/8/5/15/10 天
（09-30 / 10-02 / 10-10 / 10-15 / 10-30 / 11-09，全部 15:34:24.779211+08）——
人类不可能在同一毫秒完成六次操作。这是**一次性 INSERT 出来的演示行**，没走业务流程。

**② 该阶段是否存在有效照片关联记录？** —— **没有，一行都没有。**

```
SELECT count(*) FROM service_archive_photos WHERE archive_id = 395;
→ 0
```

六个阶段 `photo_rows` 全为 `0`。

**③ 原始照片文件是否存在？** —— **不适用**：没有 `service_archive_photos` 行
⇒ 没有 `storage_key` ⇒ 不存在"有记录但文件丢了"的情况。

**④ 新业务流程完成关键阶段是否仍强制至少一张照片？** —— **强制，且已用真实接口验证。**

造一个全新暖通档案（id=397），**不带任何照片**直接完成首阶段 `survey`：

```

▸ 不带照片完成「survey」→ HTTP 409  code=ARCHIVE_STAGE_PHOTO_REQUIRED
库内首阶段状态：pending（未通过）
```

也就是说：**当前正常操作无法绕过关键阶段照片要求**。
（核查用临时档案已删除，`SELECT count(*) ... customer_name='照片强制核查'` → 0）

## 五、日期修改保护 ✅

### 行为

| 场景 | 请求体 | 结果 |
|---|---|---|
| 只改备注 | `{note, expected_version}` —— **没有 `stage_date` 键** | 日期不变 |
| 同时改日期 | `{stage_date, note, expected_version}` | 日期更新 |

服务端 `archiveStageUpdate` 用 `paramPresence` 区分"absent"与"空串"：
- absent → **不写 `stage_date` 列**
- `''` → `ARCHIVE_STAGE_MISSING_DATE` 400（明确清空）

⇒ `ArchiveDetail.onUpdateStage` 必须**保持 `undefined`，不能用 `?? ''` 兜**。
兜错方向就是"只想改备注却改不动"或"把日期清掉"。

### 实测（CDP 拦截真实请求）

```
C1 输入备注不会改日期框的值     2026-09-30 → 2026-09-30
C2 确实发出了 archiveStageUpdate   captured
C3 请求体里没有 stage_date 键     keys=note,expected_version
C4 请求体带 note + expected_version note="封版取证294893" ver=20
C5 服务端 stage_date 仍是原值      before=2026-09-30 after=2026-09-30
C6 备注已写入服务端               note="封版取证294893"
C7 版本号前进（乐观锁正常）       v20 → v21
C8 阶段状态仍是 done              done
```

`expected_version` / 乐观锁 / `stage_updated` 审计事件（含 before/after 与
`status_unchanged`）完全未变。后续五个阶段一律未触碰。

### 显示优先级

`stage_date → completed_at → 未填写`（已完成阶段）／`today`（首次完成）。
本轮未改这个顺序，只补了"不发字段"这一层协议保证。
