## 四、真实缺陷与根因

### 4.1 B-30：卡片被 flex 压成三列

**现象**（真机 + 本轮 375/390/420 复现）：卡片里「不提供详情」四个字**竖排成 4 列单字**，整段文字裂成左中右三列。

**根因**（读 DOM/CSS，不是猜）：

```
.svc-hint { display:flex; justify-content:space-between; gap:8px; }
```

`.svc-hint` 是为「左侧一句提示 + 右侧一个操作链接」设计的。师傅失效页却把**整段长文本**塞进去：

```html
<p class="svc-hint">本机记录：…这里<strong>不提供详情</strong>；如需回看…</p>
```

文本节点被拆成 **3 个匿名 flex item**，`space-between` 把它们摊开成三列；中间的 `<strong>` 被压到最小宽度 ⇒ 每行一个字。

**量化基线**（375px，修复前）：

| 指标 | 值 |
|---|---|
| 文本块行数 | **13 行**（83 字） |
| 行宽序列 | `173,124,166,13,23,13,13,13,13,13,88,88,88` |
| 卡片高度 | 远高于正常（三列并排） |

### 4.2 B-29：429 被当成"二维码坏了"

**现象**：入口接口 429 时，页面主文案 `请求失败（HTTP 429）`，下方却写"请用手机扫描门店提供的报修二维码进入本页"。

**根因**：`fetchStoreEntry()` 直接把 `request()` 的兜底错误往外抛（429 没有专门处理），
页面拿到的只有"HTTP 429"这句话；提示区又不区分错误类型，永远是"重新扫码"。

**证据**：`docker logs svc-nginx` 里的 `"GET public-api" 429`；门禁变异复现。

### 4.3 媒体-only：能力存在，缺组合验收

**审计结论**：服务端 `if (mediaCount === 0 && dto.content.length < CONTENT_MIN)` ⇒ **有媒体时文字下限豁免**，
能力早已实现；P11-4 还专门验过"只有视频、不写文字 ⇒ 201"。
缺的是**照片 / 录音 / 组合 / 投诉**四种组合的系统验证 —— 属验收缺口，不是功能缺失。

### 4.4 上传失败恢复：部分能力已有，缺验证

前端已有：格式/大小粗筛、上传 `onerror`（网络中断）、`ontimeout`（超时）、服务端 4xx 透传、
提交按钮 `submitting` 防连点。缺的是**系统化验证**（尤其"上传成功但提交失败，媒体不丢"）。

## 八、审计结论

1. H5 的业务能力**基本齐全**，本轮不需要新增业务功能；
2. 真实缺陷只有 **B-30（布局）** 与 **B-29（文案）** 两个，均为小范围可修；
3. 媒体-only 是**验收缺口**而不是功能缺失，需补组合验证；
4. 真机证据**完全缺失**，不能由 Chromium 模拟替代 —— 这是本轮无法关闭的部分。
