# 短信开通清单（运营 / 上线准备）

> 面向**运营与上线**，不是技术报告。目标：把"客户提交后收到一条含进度链接的短信"这件事开通。
> **当前方案：短信宝（smsbao）** —— 阿里云 provider 保留兼容，但**不再需要申请阿里云 TemplateCode**。
> ⚠️ 本文件**不得**写入任何 ApiKey、明文查询 Token 或客户数据。

---

## 一、要准备的四件事

| # | 事项 | 说明 | 配到哪个变量 |
|---|---|---|---|
| 1 | **正式 HTTPS 公网域名** | 已备案、解析到本服务、证书受信、走 443 | `PUBLIC_H5_BASE_URL=https://<域名>` |
| 2 | **短信宝企业账号 + ApiKey** | ApiKey 在短信宝后台获取（**本项目只用 ApiKey**，不用"登录密码 MD5"） | `SMSBAO_USERNAME` / `SMSBAO_API_KEY` |
| 3 | **签名与模板报备** | 见第二节 | `SMSBAO_SIGN_NAME` |
| 4 | **通道切换** | 最后一步再打开 | `SMS_PROVIDER=smsbao` · `SMS_ENABLED=true` |

> 第 1 项的域名**必须是公网可解析的 HTTPS**：本项目在 **production 档会拒绝启动**；
> 若写成 `localhost` / `192.168.x.x` / 内部端口，服务**起不来**（有意护栏 ——
> 门店二维码是印出去贴在墙上的，错了无法召回）。

## 二、签名与首条模板报备

### 2.1 签名

- 官方对签名的硬性要求：正文开头必须含签名，签名是**公司/网站简称或注册商标**，
  3~10 个字符，**不能是无意义词**（如"试试看"）。
- 候选签名：**七方售后**
  ⚠️ 请确认企业资质能支持该签名（与营业执照/商标一致），**最终以短信宝审核为准**。

**关于括号形态（本项目实测的官方资料现状）**：

| 来源 | 写法 |
|---|---|
| 公开接口文档（`smsbao.com/openapi`） | 「短信内容中必须含短信签名格式为：**【公司签名】**」，范例 `【万千购】` |
| 用户后台《短信签名报备 FAQ》 | 「短信签名…用**方括号**包裹，例如**【短信宝】**」，示例 `【短信宝】您的验证码是 123456…` |
| 另有一份资料 | 写作 **`〖七方售后〗`**（鱼尾号） |

⇒ 两处官方页面**当前都写作 `【】`**，但也存在 `〖〗` 的资料。
**因此本项目不硬编码任一种，而是"以你填的形态为准"**：

- `SMSBAO_SIGN_NAME` **建议只填名字**（如 `七方售后`）⇒ 系统按官方当前写法包装成 `【七方售后】`；
- 若你填**已带括号**的整串（`〖七方售后〗` 或 `【七方售后】`）⇒ **原样使用**，
  **不会**出现 `【〖七方售后〗】` 这种重复包装。

两种填法都保证：**最终短信里签名有且只有一个**（已用逐字比对整条正文的断言覆盖）。

### 2.2 首条模板（拟报备）

**名称**：售后申请提交通知

**正文**：

```
【七方售后】您的售后申请已提交，工单号${ticket_no}。查看处理进度：${link}
```

> ⚠️ 短信宝的接口收的是**完整正文**（参数 `c`），**不识别 TemplateCode**。
> 这里的 `{ticket_no}` / `{link}` 是**平台内部渲染参数**（由本系统在发送前替换成真实值），
> **不是**要短信宝额外识别的模板变量。

**必须与供应商确认的两件事**：

1. **带动态链接的正文能否通过报备**：`{link}` 会渲染成
   `https://<固定企业域名>/p/<43 位一次性凭证>` ——
   即"**固定域名 + 每次不同的路径**"。请确认短信宝接受这种形态；
   **不能假定它接受任意动态链接**（若要求固定文案或需单独报备链接域名/短链，以审核结论为准）。
2. **变量写法**：若审核要求正文里写 `${ticket_no}` 这类占位符形式，
   以审核通过的模板为准，由开发侧把渲染结果调成一致 —— **不在代码里猜参数名**。

## 三、六个既有场景（都已在代码里，**不新增自动发送事件**）

| 场景 | 内部参数名 | 触发时机（既有） |
|---|---|---|
| 客户受理通知 | `label` / `ticket_no` / `store` / `technician` / `expected` | 门店受理/派工后 |
| 师傅任务 | `store` / `ticket_no` / `contact` / `expected` / `link` / `hours` | 派工后 |
| 师傅作业取消 | `store` / `ticket_no` / `expected` | 改派他人时 |
| 上门时间变更 | `label` / `ticket_no` / `expected` / `technician` | 预约时间变更后 |
| 评价邀请 | `label` / `ticket_no` / `link` | 工单完成后 |
| **进度查询链接（本轮重点）** | `ticket_no` / `link` | 客户提交成功时 |

> 以上六个场景的正文都能从既有业务参数渲染成**完整正文**（短信宝要求的形态）——
> 已用产品同一份渲染逻辑逐场景验过：**每条的签名都恰好出现一次、无未替换变量残留**。
>
> **不因为换供应商而增加新的自动发送事件。**
> 短信宝没有 TemplateCode 概念，所以**也不需要**为它申请六套模板 CODE。

## 四、开通前的验证步骤（按顺序做）

1. **域名可达**
   ```bash
   curl -I https://<域名>/api/svc:health      # 期望 200
   ```
2. **基址合规**：`PUBLIC_H5_BASE_URL=https://<域名>`（不带端口）后重启；服务能起来即通过生产校验。
3. **填齐凭据**：`SMSBAO_USERNAME` / `SMSBAO_API_KEY` / `SMSBAO_SIGN_NAME`（签名**不带括号**）。
4. **通道就绪但先别开发送开关**：用**运营自己的手机号**提交一张测试单，然后查：
   ```sql
   SELECT scene, provider, send_status, error_code, error_message
   FROM sms_logs WHERE scene='progress_link' ORDER BY id DESC LIMIT 5;
   ```
   - `send_status` 不应停在 `pending`；
   - 出现 `SMSBAO_*` 开头的错误码时，按下方对照表处理；
   - 手机上应收到短信，**点链接能打开那一张工单**。
5. 确认第 4 步无误后，再打开总开关：`SMS_ENABLED=true`。
6. ⛔ **不得为了"让它发出去"而修改生产校验、硬编码内网 IP、或把域名写成本机地址。**

### 常见错误码对照（官方原文）

| 返回 | 含义 | 处理 |
|---|---|---|
| `0` | **发送成功（供应商已受理）** | ⚠️ 受理 ≠ 客户已收到 |
| `30` | 错误密码 | 核对 `SMSBAO_API_KEY` |
| `40` | 账号不存在 | 核对 `SMSBAO_USERNAME` |
| `41` | 余额不足 | 充值 |
| `43` | IP 地址限制 | 在短信宝后台配置来源 IP 白名单 |
| `50` | 内容含敏感词 | 调整文案后重新报备 |
| `51` | 手机号码不正确 | 核对号码格式 |

## 五、运营另需确认的三件事

| 项 | 需要确认什么 |
|---|---|
| **单号码发送频次** | 官方说明：**默认同一号码一天只能接收 4 条**；测试期如需更多，需在后台"白名单"里添加。请确认线上活动/回访场景是否够用 |
| **账户余额** | 短信宝提供余额查询接口（`https://www.smsbao.com/query`，调用频率 ≤1 次/分钟），建议接入监控；请确认充值策略 |
| **送达报告** | ⚠️ 官方公开资料**未明确定义送达回执的字段与开通方式**（只说明了"接收用户回复"的推送接口，那是**上行回复**，不是送达回执）⇒ **列为本项目"待供应商确认"项**。**本系统不编造回调协议**；在确认之前，`delivery_status` 一直停在 `pending` 是**预期行为** |

## 七、两条**不要动**的既有契约

1. **进度 Token 可重复使用**：客户在有效期内可**反复查询**（刷新进度页、多次打开链接都行）。
   已有门禁用"连续查询 3 次都成功"钉住 —— **不要**改成"看过一次就失效"。
2. **无法安全恢复凭证的历史短信不自动补发**：库里的进度链接正文含一次性 Token 且**正文不落库**，
   异常恢复时系统会标为 `SMS_PENDING_ORPHAN_UNREBUILDABLE`（**保守不补发**）。刻意设计，**不要改成抢发**。

## 八、凭据处理（重要）

- **`SMSBAO_API_KEY` 只填在部署机器的私有环境变量里**（`.env` 已被 `.gitignore` 排除，不进仓库）。
- ⛔ **不要把 Key 发到聊天、工单、文档或截图里**。曾有一份 Key 因出现在聊天中而被视为**已暴露**：
  请到短信宝后台**轮换**，并把**旧 Key 停用**。
- 代码、`.env.example`、脚本、日志、文档里**都只保留空值或明显假值**（验收脚本用的是
  `FAKE-APIKEY-DO-NOT-LEAK-…` 这类自述式假值），**不存放任何真实凭据**。
- 服务端读取凭据后**只用于发请求**：日志里不输出原值，也不输出完整请求 URL。

---

## 九、安全约定（对开发与运维都适用）

- 短信宝发送接口是 **GET**，**完整 URL 里含 ApiKey、手机号和短信正文** ⇒
  **任何日志、异常消息、链路追踪都不得输出完整请求 URL**（已实现：异常时只记固定文案）。
- 只允许 **HTTPS**；**不跟随重定向**（避免凭据被转发到第三方）。
- `code=0` 只代表供应商**接受提交**，不代表已送达。
- 超时/连接中断时结果**未知** ⇒ 交由既有 outbox 与保守恢复策略处理，**不盲目重试**。
