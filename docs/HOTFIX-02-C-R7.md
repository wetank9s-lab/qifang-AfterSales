## 2. C4 / C5 实测结果（关键：与期望不符）

桩全程返回 `NaN`（`durReads=4`，确实被读了 4 次），但：

| 观测 | 值 |
|---|---|
| `cards` | **1**（卡片仍生成） |
| `err` | **null**（没有报错） |
| 请求 | `session` + `upload` **各 1 次** |
| `setT / clrT` | 1 / 1（超时设置后被清掉） |
| `crUrl / revUrl` | 2 / 1 |

⇒ **即使时长完全读不出来，音频仍然被上传成功、生成"已就绪"卡片。**

### 根因（读源码确认）

```ts
if (kind === 'audio' && durationMs !== null && durationMs > limits.value.audio_max_ms) { … }
```

**`null` 直接跳过时长校验并放行上传**。所以：
- 「读不出时长」对**音频不构成阻断**；
- 用户看到的「这个文件读不出时长，请重新录制」来自**另一个分支** ——
  `KIND_UNREADABLE`（**类型识别失败**），不是时长分支。

### 因此

- 执行令 C4 的期望是"不生成已就绪卡片" ⇒ **实际行为与之不符**；
- 这**不是我这轮改坏的**（该判断一直是这个写法，本轮没碰 `addCaptured`）。

**需你裁决**：音频"时长未知"应该
**ⓐ 放行**（现状：不阻塞客户，但可能超 60 秒）还是
**ⓑ 阻断**（严格执行"读不出时长就重录"）？
若选 ⓑ，最小修复是 `durationMs === null` 时对 audio/video 直接报错返回，一行判断。
