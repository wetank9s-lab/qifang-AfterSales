## 1. 问题⑦ 真实根因（我先猜错了一半，按实测纠正）

**我最初的判断**："原生 `<audio controls>` 有 300px 固有宽度、`max-width` 压不下去，把按钮挤出容器。"
**实测把这个判断推翻了一半**：

```js
document.createElement('audio'); a.controls=true; 测宽
→ 默认 300px
→ 加 max-width:170px 后 = 170px   ← 压得下去！
```

所以"控件压不下去"**不是**真因。真实原因是**同一行太挤**：

| 元素 | 宽度 |
|---|---|
| 图标 `.svc-mat-glyph` | 44（flex:none） |
| 文案 `.svc-mat-meta` | flex:1，可被压到极窄 |
| `<audio>` | 170（max-width 生效） |
| 「重录」+「删除」两个按钮 | 各 ~40（flex:none） |
| gap × 4 | 32 |

375px 下这一行已被占满 ⇒ **文案被压到几乎不可读、控件与按钮视觉错位**；
再叠加 `audio` 只有 **32px 高**、与 52px 的行高不对齐 —— 看起来就是"上传后布局错乱"。

## 4. 状态覆盖：只做到一半（如实说）

| 状态 | 状态 |
|---|---|
| 无录音 | ✅ 页面正常（三视口 0 溢出） |
| 正在上传 / 上传成功 / 失败 / 播放中 / 长文件名 / 删除后 | **❌ 未验** |

**为什么没验**：这些状态都需要 `.svc-mat` 真实渲染出来，而它只在**有一条媒体条目**时出现。
要造这条条目，只能：
① 真实上传一个音频（会写生产媒体，按令禁止），或
② 在 DOM 里手插一个假卡片（那是"直接改 DOM 制造通过"，同样禁止）。

⇒ **PENDING**。给出这条 CSS 的依据是：**实测的控件宽度 + 各元素 flex 属性 + 换行后的盒模型推算**，
不是"看着改的"。但**我不把它写成已验证效果**。
