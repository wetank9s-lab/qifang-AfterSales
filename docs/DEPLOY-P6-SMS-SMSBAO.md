用真实规则、合成数据（工单号 `FW20261022-9999`、token 43 位、域名 `https://sh.scqfls.cn`）：

| 情形 | 渲染结果 | 问题 |

## 6. 数据库 `sms.enabled` 的实际生效状态

**读取优先级（源码实测 `config-service.ts`）**：

```
DB 行 value  →  若为 null/undefined  →  seed（envKey 读 env）  →  fallback
```

⇒ **只要有行，环境变量永远不生效。**

当前实际值：

| 键 | 值 | 更新时间 |
|---|---|---|
| `sms.enabled` | **false** | 2026-10-22 11:41:17 |
| `sms.provider` | **mock** ← **关键** | 2026-10-17 13:12:08 |
| `sms.retry_count` | **1** | 2026-10-17 13:21:17 |

而 `.env.prod` 里 `SMS_PROVIDER` 是 `smsbao`（长度 6）。
**两者冲突时以 DB 为准 ⇒ 运行期实际走的是 `mock`，那个 env 里的 `smsbao` 名存实亡。**

> 这就是执行令第 9 条的答案：**不一致时 DB 生效**。
> 也因此，光把 `.env.prod` 改成 `SMS_PROVIDER=smsbao` **不会**切到短信宝 —— 必须同时改 DB 行。

⚠️ 另需注意：`APP_ENV=production` 的 profile 校验读的是 **env**（要求非 mock 才放行），
所以存在一个"**profile 校验看 env、实际发送看 DB**"的双真相结构。
这也是为什么必须两边同时核对、并**以 DB 为准验证生效结果**。
