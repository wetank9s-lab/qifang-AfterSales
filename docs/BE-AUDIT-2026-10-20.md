## 1. 审计方法与一个必须记录的方法论坑

### 1.1 做法

- 四个角色**真实登录** `https://127.0.0.1/signin`，记录：落地页 URL、侧边栏菜单、页面标题、表格列、可见按钮、正文首屏、截图（`.tmp-verify/audit-<role>.png`）。
- 角色-用户关系直接查 `rolesUsers`；数据暴露面用**原生集合接口**实测（`/api/serviceTickets:list`）。
- 脚本：`scripts/audit-backoffice-roles.mjs`（只读，不建单、不改库）。

### 1.2 坑：连续登录会把后两个角色误判成"登录失败"

第一次连续跑四角色时，`hq_after_sales` 与 `viewer` 都停在 `/signin`。
但**单独用 API 验证，四个账号全部 HTTP 200**；单独跑浏览器，两个角色也都登录成功。

原因：同一浏览器会话里连续切换账号，前一角色的状态/首屏资源未清干净 + 后台首屏加载超过原 30s 等待。
**不是产品缺陷**。修正后（每角色前 `clearBrowserCookies` + 等待 60s）四个角色均正常。

> 教训与既有铁律一致：**"登录失败"要先分清是产品坏了还是验证方法坏了**。
> 若不单独复核，就会把"hq 登不进后台"写成产品缺陷——那是假红。

## 4. BE-02 · Excel 导入与历史售后档案

### 4.1 已有能力（核实结果）

| 能力 | 现状 | 证据 |
|---|---|---|
| 6 张历史表 | **存在，全部 0 行** | `historical_import_batches/rows/candidates/reviews`、`historical_service_archives`、`historical_ticket_conversions` |
| 服务端导入 action | 存在（`createHistoricalImportHandlers`，含 limits/store/hash） | `actions/svc/historical-import.ts` |
| 页面 | seed 脚本可建「历史数据导入」「历史售后档案」（NAV 组「售后工单」） | `scripts/seed-historical-*-page.mjs` |
| **是否已挂到菜单** | ❌ **四角色菜单里都没有** | 本轮四角色实测 |

> 结论：**能力有底座、页面有脚本、但没有出现在任何角色的真实菜单里**。
> 不能写"已实现"，也不能写"完全缺失"——准确表述是**未接线（未挂菜单/未授权）**。

### 4.2 必须区分的两类导入

| | A. 历史服务记录 | B. 当前待处理工单 |
|---|---|---|
| 产物 | `historical_service_archives`（只读档案） | `serviceTickets`（NEW，进入日常流程） |
| 是否影响 SLA/KPI | **否** | **是** |
| 是否生成工单 | 否 | 是（受控批量建单） |
| 默认行为 | 导入即归档 | **必须显式选择**，绝不默认 |

> 🔴 绝不允许"把历史 Excel 每一行默认转成 NEW"——那会把三年历史一次性变成 2000 张待办，直接压垮门店工作台。

### 4.3 门店端流程（设计）

```
① 选择用途  ──▶ ② 上传 Excel ──▶ ③ 字段映射 ──▶ ④ 清洗预览
   (A 档案 / B 当前工单)                                  │
                                                          ▼
⑥ 查看结果 ◀── ⑤ 确认导入 ◀── 异常确认（逐行，可导出问题行）
```

每步的硬要求：

| 步 | 要求 |
|---|---|
| ① | 默认选中 **A 档案**；选 B 必须二次确认并填写用途说明 |
| ② | 只收 `.xlsx`；≤ 5MB / ≤ 2000 行；**文件 hash 去重**（同文件重复上传直接拒绝） |
| ③ | 列映射可保存为模板；未映射的必填列禁止下一步 |
| ④ | 逐行显示：可导入 / 警告 / 错误（含行号、原值、原因）；错误行可下载 |
| ⑤ | **只导入"可导入"行**；部分失败不回滚已成功行，但批次状态标 `partial` |
| ⑥ | 显示：成功 N / 跳过 N / 失败 N + 失败行下载 + 批次号 |

**门店归属**：Excel 里的门店列只能用于**校验**，不能用于"认领"。
归属未确认时——不得确认导入、不得归档、不得生成服务单。

### 4.4 B 类批量建单的硬约束

| 约束 | 做法 |
|---|---|
| 每行校验 | 复用现有建单 DTO（手机号、类型、内容下限）；不另写一套 |
| 幂等 | 批次内 `row_hash` 唯一 + 全局 `(store, 客户手机号, 内容摘要, 日期)` 去重；重复行标 `duplicate` 跳过 |
| 部分失败 | 逐行事务；失败行不影响其它行；批次可**从失败行重试** |
| 短信副作用 | **默认不发短信**；需要通知时显式勾选，且逐行限流（避免 2000 条短信轰炸） |
| 审计 | 批次、操作人、文件 hash、映射模板、成功/失败计数全部落 `historical_import_batches` |
| 回滚 | 支持"按批次撤销未派工的 NEW 工单"（已派工的不撤销，转人工） |

### 4.5 历史档案查询

必须支持：客户姓名、手机号、门店、家电品类、日期范围。
**不能只展示批次号/归属范围/解析结果**——那是导入日志，不是档案。

关联：当前工单详情里，若该客户手机号命中档案，显示「历史服务 N 次」并可展开（只读）。
**按授权门店过滤**；跨店命中不展示。

## 5. BE-03 · 短信配置中心

### 5.1 现状（真实消费点）

`SMS_SCENE` 至少 7 个值，其中 **6 个有真实调用点**：

| 场景 | 调用点数 | 收件人 | 关闭风险 |
|---|---|---|---|
| `dispatch_customer` | 3 | 客户 | 客户不知道师傅要来 |
| `technician_task` | 3 | 师傅 | 师傅不知道任务（**高危**） |
| `technician_assignment_cancelled` | 3 | 原师傅 | 师傅白跑一趟（**高危**） |
| `dispatch_update` | 5 | 客户 | 时间变更不同步 |
| `review_invite` | 3 | 客户 | 无评价入口 |
| `manual_resend` | 3 | 手动 | 门店手工补发 |

UX-01C R8 冻结的是「短信通知」这一页的三项设置；**不能因为升级界面而改语义**。

### 5.2 页面结构（5 个 Tab）

```
短信总览 | 通道管理 | 场景发送规则 | 模板管理 | 日志与回执
```

| Tab | 内容 | 关键约束 |
|---|---|---|
| 总览 | 今日发送/失败、通道健康、最近失败 Top5 | 只读 |
| 通道管理 | 通道列表（provider/状态/模板数/最近发送） | 支持的 provider 来自**代码常量**；不可动态新增 provider 实现，只能配置已支持的 |
| 场景规则 | 每个 scene 一行：开关、通道、模板、收件人 | 关闭**高危场景**（`technician_task` / `technician_assignment_cancelled`）需二次确认 + 填写原因 + 写审计 |
| 模板管理 | 模板 code ↔ 场景映射、审核状态 | 不改供应商侧模板内容，只做映射 |
| 日志 | 发送记录、失败原因、回执 | 复用 `smsLogs`，不新建表 |

### 5.3 兼容默认（最重要的一条）

升级后**默认值必须等于现状**：所有场景保持"开"，通道保持当前 provider。
任何"默认关"都会让本来该发的短信静默消失——这比多发的危害大得多。
上线前用一条**对照门禁**：升级前后同一夹具工单的 `sms_logs` 场景集合必须一致。

### 5.4 凭据管理：A / B 两方案

| | **A. 环境变量 + 受控部署** | **B. 后台凭据管理** |
|---|---|---|
| 谁能改 | 运维（改 `.env` + 重启） | hq_admin（页面操作） |
| 密钥落点 | 进程环境 | KMS/加密表（**绝不明文进 `serviceSettings`**） |
| 轮换 | 改环境变量 + 重启（有中断） | 页面轮换，双密钥过渡 |
| 审计 | 部署记录 | 每次新增/轮换/停用写审计（谁、何时、哪个 provider） |
| 泄露面 | 服务器/部署系统 | 后台 + 加密存储（面更大） |
| 成本 | 低 | 高（加密、权限、审计、回滚） |
| 建议 | **首发期选 A** | P11-6 之后再评估 |

硬红线（两方案都适用）：API Key **不得**写入 `serviceSettings` 明文、原生日志、浏览器响应、Git。

> 首发服务商未联调：**mock PASS ≠ 真实短信 PASS**（R-1 仍是发布阻断项）。

## 7. BE-05 · 总部售后工作台

### 7.1 现状

- `hq_after_sales` 落地是**列表**，不是工作台。
- 已有 API：`dashboardSummary`（登录即可）、`reportKpi`（PRIVILEGED）、`exportTickets`（**仅 hq_admin**）。
- 已有 `runSlaScan` 与 12 项冻结 KPI 算法。

### 7.2 设计

```
┌ 总部售后工作台   今日 | 本月 | 本年 | 自定义 ────────┐
│ ┌新增┐ ┌完成┐ ┌在办┐ ┌待确认┐ ┌超时┐               │
│ │ 128│ │ 96 │ │ 41 │ │  7  │ │ 12 │  每个数字标口径│
│ └────┘ └────┘ └────┘ └────┘ └────┘               │
│ 趋势（近 30 天新增/完成）                            │
│ 门店对比表：门店 | 新增 | 完成 | 积压 | 超时 | 平均时长│
│ 异常看板：厂家未跟进 / 预约逾期 / 回执待审核 / 返工  │
│ [导出管理汇总 .xlsx]                                 │
└──────────────────────────────────────────────────────┘
```

硬约束：

1. **KPI 算法不复制**：直接复用 `reportKpi`/`dashboardSummary`，新页面只做编排与展示。
2. **SLA 单一事实源**：`runSlaScan` 的判定不重写；工作台只读结果。
