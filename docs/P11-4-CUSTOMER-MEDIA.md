## 12.2 数据模型（20 张表，12→20）

| 表 | 作用 |
|---|---|
| `customer_media_sessions` | **上传会话**：匿名创建、120 分钟 TTL、状态机（open/bound/expired/voided）。🔴 `session_token_hash` **UNIQUE** |
| `customer_medias` | **媒体文件**：类型 / storage_key / mime / size / duration / 会话与工单关联。🔴 `(session_id, storage_key)` **UNIQUE** = 幂等的结构性保证 |
| `service_tickets` 加三列 | `progress_token_hash`（UNIQUE）/ `progress_token_expires_at` / `progress_token_revoked_at` |

设计要点：

- **会话层**是为了解决"未完成上传"：媒体先挂会话、提交时原子绑工单 ⇒
  任何"有会话没工单"的媒体都能被精确定位并清理。
- **幂等靠唯一索引**而不是"先查后写"（TOCTOU，并发下会漏）。
- 进度 Token 与评价 Token **完全分离**（用户 C 条明令）：不共用列、不共用常量、不共用短链。

## 12.3 服务端：三个匿名媒体动作 + 一个只读查询

| 接口 | 凭证 | 守卫 |
|---|---|---|
| `POST /api/public/media/session` | 无 | IP 频控（`media_session` 桶）+ **明示媒体授权 `media_consent`** |
| `POST /api/public/media/upload` | `X-Media-Session` | IP 频控（`media_upload` 桶）+ 会话有效性 + 契约校验 |
| `GET  /api/public/media/files/<id>` | 会话 token **或** 进度 token | 属主校验（媒体的 session/ticket 归属） |
| `GET  /api/public/progress/<token>` | 进度 Token | 形状 / 撤销 / 有效期 / 关闭后 30 天 |

**为什么媒体授权要单独明示**：`publicTicket:create` 的"提交即同意"只覆盖"提交服务请求"这一件事；
上传画面里可能有客户家门牌、家庭成员 —— 那属于另一类处理，不能吃那份依据
（`public/ticket.ts` 里本来就写着这条红线）。界面取"**行为即同意**"（常驻一句话 + 点上传），
而不是再弹一个勾选卡片（用户 A 条明确去掉了那种卡片）。

**图片管线复用而非复制**：`PhotoService.normalizeImage()` 被抽成公共方法，
师傅照片与客户媒体**共用同一段**（magic bytes 判定 → 剥 EXIF/GPS → EXIF Orientation 转正 → 剥离回查）。
第一版想把逻辑复制一份，被自己的工程铁律挡下：那一行行都对应一个踩过的坑。

## 12.4 冻结契约的校验（全部按服务端判定）

| 约束 | 判据 |
|---|---|
| 图片 1~3 张 | 按**已有行数**判（重试不占额度） |
| 语音 ≤60s / 视频 ≤30s | 从**容器里解析时长**（WAV/MP4/WEBM/OGG），解析不出 ⇒ 422 fail-closed |
| 文字或媒体至少一种 | 会话里没有文件且文字为空 ⇒ 422 `TEXT_OR_MEDIA_REQUIRED` |
| 单文件 8MB / 会话 5 个 | multer 流式限 + 服务端二次判 |
| 类型 | **magic bytes**，不信 Content-Type 与扩展名 |

## 14.1 独立工具复核：真实产物**有** Tracks（DEV-183）

`scripts/ebml-probe.py`（按 EBML 规范**解析元素树**，不是字节搜索）复核真实 Chromium 产出：

| 真实样本 | 浏览器自报 mime | 大小 | Tracks | TrackEntry | TrackType | Duration |
|---|---|---|---|---|---|---|
| `audio-chrome.webm` | `audio/webm;codecs=opus` | 40,666 B | **1 @195** | 1 | **[2] = audio** | 2940 ms |
| `video-chrome.webm` | `video/webm;codecs=vp8,opus` | 126,326 B | **1 @195** | **2** | **[2, 1] = audio + video** | 2940 ms |

**上一轮"没有 Tracks"的真因**：字节搜索命中了 **SeekHead 里的 `SeekID`** ——
`0x1654AE6B` 作为「对元素 ID 的**引用**」出现在那里，从那儿往后找 `0x83`
自然命中了 Info 的 `MuxingApp`（`83 0F 42`）。

⇒ **"在字节流里找 ID"不是解析。** 引用、Cues、甚至码流里都会出现这些字节。

**据此**：`declared_kind` 兜底**整体撤除**（前端不再发送、服务端参数不再使用）。
服务端现在**只从文件内容**判定类别与时长 —— 完全满足用户"不得凭客户端声明决定限制"。

## 14.2 服务端改为**规范元素树**解析（DEV-183~186）

`media-format.ts` 里换成按 EBML 规范走元素树，并按真实文件修掉三个缺陷：

| 缺陷 | 后果 |
|---|---|
| 未知长度用**数值**判断（8 字节 VINT 超出 JS 安全整数 ⇒ 精度丢失） | 长度未知的 Segment 被判成超大尺寸 ⇒ **整个解析在 Segment 处停住**，真实文件全部读不出类别 |
| `TrackType` 的值按 **VINT** 读（它其实是 1 字节**无符号整数**） | 值 `0x02` 被当成"7 字节 VINT" ⇒ 越界 ⇒ 丢掉 |
| 收集够就 `return`（"提前结束"） | 录像有**两条轨道**，读到第一条音频轨就返回 ⇒ **整段录像被判成 audio** ⇒ 视频 30 秒上限形同虚设 |

同时加了**资源限制**（用户要求）：元素数上限 20,000、深度上限 6、**跳过 Cluster**
（里面是上千个 SimpleBlock 纯码流，Tracks/Duration 都在它之前）。
文件大小上限仍由 `CUSTOMER_MEDIA.MAX_FILE_BYTES`（8MB）在前置拦下。
