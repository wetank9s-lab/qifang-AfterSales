## 12.2 数据模型（20 张表，12→20）

| 表 | 作用 |
|---|---|
| `customer_media_sessions` | **上传会话**：匿名创建、120 分钟 TTL、状态机（open/bound/expired/voided）。🔴 `session_token_hash` **UNIQUE** |
| `customer_medias` | **媒体文件**：类型 / storage_key / mime / size / duration / 会话与工单关联。🔴 `(session_id, storage_key)` **UNIQUE** = 幂等的结构性保证 |
| `service_tickets` 加三列 | `progress_token_hash`（UNIQUE）/ `progress_token_expires_at` / `progress_token_revoked_at` |

设计要点：

- **会话层**是为了解决"未完成上传"：媒体先挂会话、提交时原子绑工单 ⇒
  任何"有会话没工单"的媒体都能被精确定位并清理。
- **幂等靠唯一索引**而不是"先查后写"（TOCTOU，并发下会漏）。
- 进度 Token 与评价 Token **完全分离**（用户 C 条明令）：不共用列、不共用常量、不共用短链。

## 12.3 服务端：三个匿名媒体动作 + 一个只读查询

| 接口 | 凭证 | 守卫 |
|---|---|---|
| `POST /api/public/media/session` | 无 | IP 频控（`media_session` 桶）+ **明示媒体授权 `media_consent`** |
| `POST /api/public/media/upload` | `X-Media-Session` | IP 频控（`media_upload` 桶）+ 会话有效性 + 契约校验 |
| `GET  /api/public/media/files/<id>` | 会话 token **或** 进度 token | 属主校验（媒体的 session/ticket 归属） |
| `GET  /api/public/progress/<token>` | 进度 Token | 形状 / 撤销 / 有效期 / 关闭后 30 天 |

**为什么媒体授权要单独明示**：`publicTicket:create` 的"提交即同意"只覆盖"提交服务请求"这一件事；
上传画面里可能有客户家门牌、家庭成员 —— 那属于另一类处理，不能吃那份依据
（`public/ticket.ts` 里本来就写着这条红线）。界面取"**行为即同意**"（常驻一句话 + 点上传），
而不是再弹一个勾选卡片（用户 A 条明确去掉了那种卡片）。

**图片管线复用而非复制**：`PhotoService.normalizeImage()` 被抽成公共方法，
师傅照片与客户媒体**共用同一段**（magic bytes 判定 → 剥 EXIF/GPS → EXIF Orientation 转正 → 剥离回查）。
第一版想把逻辑复制一份，被自己的工程铁律挡下：那一行行都对应一个踩过的坑。

## 12.4 冻结契约的校验（全部按服务端判定）

| 约束 | 判据 |
|---|---|
| 图片 1~3 张 | 按**已有行数**判（重试不占额度） |
| 语音 ≤60s / 视频 ≤30s | 从**容器里解析时长**（WAV/MP4/WEBM/OGG），解析不出 ⇒ 422 fail-closed |

| 类型 | **magic bytes**，不信 Content-Type 与扩展名 |

## 14.1 独立工具复核：真实产物**有** Tracks（DEV-183）

`scripts/ebml-probe.py`（按 EBML 规范**解析元素树**，不是字节搜索）复核真实 Chromium 产出：

| 真实样本 | 浏览器自报 mime | 大小 | Tracks | TrackEntry | TrackType | Duration |
|---|---|---|---|---|---|---|
| `audio-chrome.webm` | `audio/webm;codecs=opus` | 40,666 B | **1 @195** | 1 | **[2] = audio** | 2940 ms |
| `video-chrome.webm` | `video/webm;codecs=vp8,opus` | 126,326 B | **1 @195** | **2** | **[2, 1] = audio + video** | 2940 ms |

**上一轮"没有 Tracks"的真因**：字节搜索命中了 **SeekHead 里的 `SeekID`** ——
`0x1654AE6B` 作为「对元素 ID 的**引用**」出现在那里，从那儿往后找 `0x83`
自然命中了 Info 的 `MuxingApp`（`83 0F 42`）。

⇒ **"在字节流里找 ID"不是解析。** 引用、Cues、甚至码流里都会出现这些字节。

**据此**：`declared_kind` 兜底**整体撤除**（前端不再发送、服务端参数不再使用）。
服务端现在**只从文件内容**判定类别与时长 —— 完全满足用户"不得凭客户端声明决定限制"。

## 15.1 BUG 1 · 录音"读不出时长"（DEV-191）

**实证**（服务端日志，非推测）：

```
10:13:38  会话 481 存入 #305：image/jpeg 310707B 1200x1600        ← 照片上传成功
10:13:45  response POST publicMedia:upload 422 errorCode:"DURATION_UNREADABLE"   ← 录音失败
```

⇒ **照片通、录音不通**；且错误是 `DURATION_UNREADABLE`（不是 `KIND_UNREADABLE`）
⇒ 说明**种类判出来了**，卡在**时长**。

**根因**：`mp4DurationMs` **只读 `moov > mvhd > duration`**。
iOS 的 `MediaRecorder` 产出 `audio/mp4` 且是**流式分片写出的** ⇒ `mvhd.duration` 常为 **0**
（录制过程中无法回填总时长），真实时长只在 `mehd` / `mdhd` 里。
⇒ 客户端本地能正常试听（浏览器自己知道采样数），服务端读到 0 ⇒ 判"读不出"。

**修法**（按 fMP4 规范依次尝试三来源，**读不出仍 fail-closed 拒绝**，不是把提示改软）：

1. `moov > mvhd > duration`（普通 MP4）
2. `moov > mvex > mehd > fragment_duration`（**分片 MP4 的总时长**，单位是 mvhd 的 timescale）
3. `moov > trak > mdia > mdhd > duration`（轨道时长，取最长轨道）

**独立复核**：新增 `scripts/mp4-probe.py`（按 ISO-BMFF **box 树**解析，独立于 TS 实现），
对 Chromium 真实产出的 fMP4 样本给出 `mvhd v1 ts=1000 dur=2453` + `moof` + `mvex/trex`
⇒ "分片 + mvhd 有效"这条路已通；iOS 若是 `dur=0` 则走 mehd/mdhd 兜底。

**新增夹具**：`test-fixtures/real-media/audio-chrome-fmp4.mp4`（Chromium 真实产出 41KB）。

**新增诊断能力**（复测失败时不用猜）：解析失败时服务端记一行**只含容器结构**的日志
（box 类型 / timescale / duration / track 类型 + 前 12 字节 magic，**不含任何媒体内容**），
例如 `结构=head=...|ftyp|moov|mvhd v1 ts=1000 dur=0|mvex|mehd fragment_duration=0|...`。

## 15.2 BUG 2 · 有媒体却要求填 5–500 字（DEV-192）

**实证**：服务端日志 `10:14:56 / 10:15:00 POST publicTicket:create 422 INVALID_CONTENT`。

1. 组件在**每次上传成功后**再同步一次会话（幂等）；
2. 父组件**提交前显式核对**「有成功材料 ⇒ 必须有会话」「不在上传中」，
   不一致就当场说清（提示"材料上传状态异常，请删除后重新添加照片或录音"），**不再静默提交**；
3. 组件新增 `currentSession()` / `hasPending()` 供父组件核对。

**文案统一**（用户指定口径）：服务端**两处**校验（守卫链 + create）与客户端统一为
**「请描述问题或添加照片、录音、视频」**；超长仍如实提示「描述最多 500 字…请精简一下」；
**投诉侧同一句**（原来会说"报修内容"，与客户所选类型不符）。

## 16.3 BUG 2 真断点：`normalize()` 的**字符串白名单把对象字段丢掉了**（DEV-194）

**用真实页面点击 + 抓请求体**（`scripts/verify-submit-links.mjs`）拿到两条互相矛盾的证据：

| 来源 | 结果 |
|---|---|
| 组件诊断（`console.info`，看的是 `draft`） | `media_session=yes 已上传材料数=1` |
| **CDP 抓到的实际请求体** | `字段=store_code,ticket_type,content,...` **`media_session=NO`** |

⇒ 断点**不在组件、不在 draft 组装**，而在 **`draft` → 请求体**之间。

**根因**：`h5/src/api/public.ts` 的 `normalize(draft)` 是"**只取字符串白名单并 trim**"
（返回 `Record<string, string>`），而 `media_session` 是 `{ id, token }` **对象** ⇒
**根本不在白名单里** ⇒ 被静默丢掉。

**为什么三轮没发现**：我此前所有验证都**手工构造完整 JSON** 直接打接口，
**完全绕过了 `normalize()` 这一层**。⇒ 这就是用户要求"必须使用真实 H5 页面点击提交、
检查实际发出的请求体；不得只用 Node 测试手工构造请求"的原因 —— 那条要求直接命中要害。

**修法**（最小必要）：
1. `normalize()` 返回类型改为 `Record<string, unknown>`，并把 `media_session`
   （要求 `id` 是数字且 `token` 非空）**原样纳入**；
2. `fingerprint()` 用**会话 id** 参与（而不是把对象塞进 `key=value` 拼串变成 `[object Object]`）——
   语义："**换了材料就是另一次提交意图**"，否则客户删掉照片重拍后点提交会被当成重试而**回放旧结果**；
   token **不进**指纹（每次建会话都不同，进来会让任何重放失效）。

**服务端判据同步收紧**（用户明确要求）：内容下限**不再**看"请求里有没有 `media_session` 这个键"
（那等于凭客户端声明放宽），改为在**守卫链之后**按 `countForSession()` 查到的**真实媒体数**判定：
- 媒体数 > 0 ⇒ 文字可以为空；
- 媒体数 = 0 ⇒ 文字必须 ≥ 5 字（否则回「请描述问题或添加照片、录音、视频」）。

**改动中引入并当场修掉的一处回归**：删掉 `parseDto` 里的 `mediaSession` 局部变量后，
返回值仍在引用它 ⇒ 提交 500（`mediaSession is not defined`）。
**是真实页面探针立刻抓到的**（页面横幅"服务端异常"）—— 这条探针的价值再次被印证。

## 16.4 BUG 1 真断点：iPhone 的 webm **没有 `Info > Duration`**（DEV-195）

⇒ iPhone 产出的是 **webm**（不是 mp4！），音轨能识别（`trackTypes=[2]`），

⇒ 上一轮补的 `mvhd/mehd/mdhd` 是 **mp4** 的三来源，对 webm 一点用没有。

**修法**：webm 时长改为两个来源，**优先** `Info > Duration`，缺失时用
**分片时间戳**：最后一个 `Cluster` 的 `Timecode` + 该 Cluster 内 `SimpleBlock` 的最大相对时间戳
（× `TimecodeScale`）。

⚠️ 这里同时修掉了上一轮为"省遍历"而做的**跳过 Cluster** ——
那个优化**恰好把唯一的时长来源也跳掉了**。防 DoS 靠**元素数预算**（现已提到 40k），
而不是靠跳过合法结构。

**夹具**：`audio-chrome-noduration.webm`（真实 Chromium 录音，Duration 置 0 ⇒ 等价"没有"），
由 `scripts/make-noduration-variant.py` 派生。

**安全边界仍然守住**（实测，不是推断）：

| 样本 | 结果 |
|---|---|
| 无 Duration + 真实 2.9 秒 | ✅ 200，服务端推出 2940ms |
| **无 Duration + 真实 65 秒** | ✅ **413 AUDIO_TOO_LONG**（分片推算正确算出 > 60 秒） |
| 有 Duration 的 65 秒（对照） | ✅ 413 AUDIO_TOO_LONG |

⇒ 60 秒限制**没有放宽**，也没有依赖客户端上报的时长。

## 18.2 真断点：响应收敛白名单把 `progress_token` 吃掉了（DEV-199）

`h5/src/api/public.ts` 的 `send()` 里有一段**响应字段收敛**（Phase 3 就有的安全设计）：

```ts
// "即使将来后端多回一个 id/handler，页面也拿不到它"
return { ticket_no: …, store_name: …, created_at: … };   // ← 没有 progress_token
```

而 `TicketCreated` 接口里**声明了** `progress_token?: string`（第一批加的）。
⇒ **类型上有、运行时没有** ⇒ 成功页 `progressToken` 恒为空 ⇒
`<button v-if="progressToken">` **根本不渲染**。

**这与 DEV-194（`normalize` 丢掉 `media_session`）是同型反模式、方向相反**：
一个滤**出站请求**、一个滤**入站响应**。

⇒ **修法**（最小契约补充，用户 B 项明确允许）：
在收敛白名单里放行 `progress_token`（且只放行非空值）。
**没有新发凭证、没有新造 API、没有用工单号拼地址**。

## 18.3 顺带抓到我自己的**假绿**（DEV-199 的另一半，比缺陷本身更重要）

修好产品后，我实测**之前**的成功页：

```
成功页 URL 的 query 键 : [no, store, at, k]     ← 没有 pt
页面上的按钮          : ["复制工单号","再报一单"]
「查看处理进度」存在   : ❌
```

⇒ 但 `verify-customer-media-ui.mjs` 一直显示 **24/24 全部通过**！

**为什么**：那条断言被包在 `if (node.nodeId) { … }` 里，而选择器写的是
`[data-testid="pick-from-album"] input`（**后代**选择器）—— 第三批我把 `data-testid`
挂到了 `<input>` **自己身上**，于是 `nodeId = 0` ⇒ **整块（上传 → 提交 → 进度入口断言）
被静默跳过**，而那几条断言**从来没跑过**。

⇒ 这正是项目铁律「**断言不会变红 = 没有断言**」的活标本：
**门禁里凡是"条件不满足就跳过"的分支，都会在元素改名/移位后变成静默的假绿。**

**修法**：
1. 选择器改为 `input[data-testid="pick-from-album"]`（自身）；
2. **找不到元素直接判红**，不允许跳过（加一条前置断言"相册入口可被定位"）；
3. 成功页断言**加可见性判据**（`getBoundingClientRect` 宽高 > 0）——
   "元素在 DOM 里"不等于"客户看得见"；
4. 加"URL 必须带 pt"的断言（这次缺陷的直接判据）。

修完后门禁从 24 项变成 **34 项** —— 多出来的 10 项就是**以前从来没跑过**的那些。

## 22. P11-4 第十轮：短信宝（smsbao）provider 适配（2026-10-14）

## 22.1 官方接口事实（按官方文档，非推断）

来源：`https://www.smsbao.com/openapi/213.html`（《发送国内短信接口API》）

| 项 | 官方原文要点 |
|---|---|
| 地址 | 安全接口 **`https://api.smsbao.com/sms`**（支持 HTTPS） |
| 方式 | **GET** |
| 参数 | `u` 用户名（必填）· `p` 密码MD5 **或 ApiKey（推荐使用更安全）** · `g` 产品ID（**否**，不填走通用产品）· `m` 手机号（必填）· `c` **完整内容，UTF-8 URL ENCODE**（必填） |
| 返回 | **"返回 '0' 视为发送成功，其他内容为错误提示内容"** |
| 错误码 | `30` 错误密码 · `40` 账号不存在 · `41` 余额不足 · `43` IP地址限制 · `50` 内容含有敏感词 · `51` 手机号码不正确 |
| 签名 | 官方硬性要求正文含 **`【公司签名】`**（全角方括号，3~10 字） |

⚠️ **一处与用户口径不符、以官方为准**：用户给的签名候选写作 `〖七方售后〗`，
而官方要求 `【七方售后】`。**本项目按官方实现** —— 而项目既有的 `【{sign}】` 渲染
**正好合规**，因此**不需要任何括号归一化**。

## 22.2 实现（最小必要）

| 改动 | 内容 |
|---|---|
| `constants.ts` | `SMS_PROVIDER_NAME` 加 `SMSBAO: 'smsbao'`（**不新增 scene、不改触发时机**） |

| `services/sms-preview.ts` | **新增纯函数 `renderSmsPreview`**：把 `SmsService.renderPreview` 的纯逻辑原样抽出，`renderPreview` 改为委托（**行为不变**）。理由：短信宝收发**完整正文**，这份渲染结果**就是真实发送内容**，必须能被验收直接调用 —— 在测试里再写一遍替换逻辑就是两份实现 |

## 22.3 安全实现（用户点名的 GET 接口风险）

| 风险 | 处理 |
|---|---|
| **URL 含 ApiKey + 手机号 + 正文** | 🔴 **绝不输出完整 URL**。关键在于：Node fetch 异常消息**常内嵌完整 URL**（`fetch failed: https://…?p=KEY&m=…`）⇒ provider 在 catch 里**只输出自己构造的固定文案**，不拼接 `error.message` |
| 明文传输 | 只允许 `https://api.smsbao.com`（断言过 protocol + host + path） |
| 重定向可能外泄凭据 | 请求带 `redirect: 'error'`（**不跟随**） |
| 受理 ≠ 送达 | `code=0` 只设 `accepted:true`；`deliveryStatus` 由类型层强制为 `'pending'` |
| 超时/中断结果未知 | 只标 `accepted:false` + `SMSBAO_TIMEOUT`/`SMSBAO_NETWORK_ERROR`，**不自行重试**，交由既有 outbox/B-16 |

## 22.5 过程中抓到的一个**真实缺陷**（DEV-200）

上一轮我用脚本往 `SMS_TEMPLATE_TEXT` 补 `PROGRESS_LINK` 文案时，**实际插进了
`SMS_RECIPIENT_KIND` 表**（该表的值域是收件人类型 `CUSTOMER`/`ANY`）。
后果有两层：

1. `SMS_TEMPLATE_TEXT[PROGRESS_LINK]` 仍为空 ⇒ 渲染走 fallback
   （`【签名】progress_link：{...}`）⇒ **正是本轮精确断言"与拟报备文案逐字一致"抓住的**；
2. 更隐蔽：它在 `SMS_RECIPIENT_KIND` 里造成**重复键**，把该 scene 的收件人类型
   覆盖成了一句中文文案 ⇒ 收件人类型查找被污染。

**为什么没被发现**：脚本打印了"已补 PROGRESS_LINK"（**内容确实写进去了，只是写错了表**），
而 TS 不报错（值恰好也是 string）⇒ **只有精确的业务断言能发现**。
