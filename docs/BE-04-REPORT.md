## 3. 为什么其余 4 项仍未关闭（技术阻塞，不是"没跑"）

### 3.1 日期四模式 + 快捷 —— 需要新增筛选组件能力，不是改配置

实测事实：

- `filterForm` 的字段只接受**字符串名**（`fields: ['createdAt', ...]`），无法给单个字段配 `picker` / `presets`；
- 当前 `createdAt` 渲染成一个日期控件，打开后 **`.ant-picker-presets` 为空**，只有组件自带的「今天」；
- 「按日 / 按月 / 按年 / 自定义」是**四种互斥模式**，一个字段表达不了，需要：
  - 方案 A：扩展 seed 的 filterForm 支持"字段配置对象"（`{field, component, picker, presets}`）并在 builder 里映射；
  - 方案 B：写一个本页专用的受控筛选组件（你已授权），但要接进 flow-engine 的 `filterManager`，并自证它设置的是**表格的真实 filter**。
- 这两条都不是"改个 JSON 值"，本轮没有安全完成，**没有动**。

> 我拒绝用"临时 DOM 操纵"或"前端假过滤"来凑，那是你明确禁止的。

### 3.2 所属门店列 —— 字段在清单里但没渲染

- `TICKET_LIST_FIELDS_HQ = ['ticket_no','store', ...]`，`store` **确实在**字段清单里；
- 但浏览器实测表头 **13 列没有门店列**；
- 说明 `store` 作为 **belongsTo 关联**，在表格列模型里需要额外的显示字段配置（targetKey/display），而 seed 的 `fields` 只声明了字段名。
- 修法要动列模型生成逻辑，属结构性改动，本轮未做。

### 3.3 筛选 UI 端到端闭环 —— 依赖 3.1/3.2

只有"日期四模式 + 门店筛选"真实可用后，端到端点击闭环才有意义。当前可点，但"选某月/某年"根本不存在，无法给出合规的端到端证据。

### 3.4 反向 A / B —— 当前没有"产品侧可变异点"

- 日期筛选由 **NocoBase 原生 filter** 完成，产品侧没有自研的日期边界计算函数可变异；
  改测试里的边界等于"改期望制造假红"，你已明确禁止。
- 门店范围由 **ACL + 行级 scope** 决定；变异需要改角色/ACL，而你禁止在真实环境做破坏性变异，本轮也没有隔离环境可用。

> 这两项要等 3.1（自研筛选组件，届时会有真实的边界计算可变异）和独立测试环境就绪后才有意义。

## 4. 本轮又修掉 3 个"验证器自己错"（都写进注释了）

| # | 假象 | 真相 |
|---|---|---|
| 1 | 空 `<td>` 被判"逐字竖排" | 空元素 `textContent` 为空，Range 仍产生极窄 rect ⇒ 必须 `text.length >= 4` 才测 |
| 2 | 已登录状态导航 `/signin` 超时 | SPA 路由接走，等不到登录表单 |
| 3 | 裸 `fetch('/api/auth:check')` 返回 401 | **NocoBase 的 token 由 axios 拦截器加**，裸 fetch 不带 Authorization ⇒ 用"token 在 + 表格有数据 + 仍在 /admin"判会话 |

第 3 条尤其危险：如果不核实，会把**五档全部判成"会话失效"**，得出"布局全不达标"的完全错误结论。
