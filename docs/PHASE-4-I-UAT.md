| 阶段 | 内容 |

| ① 全量验证 | `verify-config` → `verify-plugin-load` → `verify-client-logic` → `verify-phase3-h5` → `smoke-test`，**脚本间自动冷却 25s** |

为什么顺序不能反：**`smoke-test` 会真实调用匿名报修接口造工单**（并发 / 幂等 / 探针），

25s 冷却是为了等 nginx 匿名接口的令牌桶回填（`svc_public: rate=30r/m`，约 20s 回满）。
**没有这个冷却，串跑时 `smoke-test` 必定多出 2~3 条 429 假红**（DEV-63）—— 那是限流不是缺陷，
但混在真红灯里会把排查方向带偏。看到 429 提示时**不要去改业务代码**。

## 5. 走查结束后的清理（**必做**）

> ⚠️ **走查后默认执行 `--disable`，不要执行 `--delete`**（复核方 2026-09-22 裁定）。

**为什么不是直接物理删除**：走完第 2 步之后 UAT-A 通常已经是主工单的 `handler_user_id`，
受理 / 派工 / 改派 / 改约每条 `ticket_events` 的 `operator_user_id` 也指向它。
而 UAT 工单是**要保留的验收证据**。此时物理删除用户行，会让工单与事件的引用变成空引用 ——
证据"还在"，但**说不清是谁做的**，审计上不可解释。

本项 NocoBase 的 `users` 表**没有**可用的禁用字段（实测 `\d users` 无 `disabled` / `enabled`），
因此按复核方给的降级口径执行：

```bash
# ① 【默认】停用：撤角色 + 撤门店映射 + 重置随机口令 + 阻断登录，**保留 users 行**
node scripts/uat-accounts.mjs --disable

# ② .env 里残留的 UAT_*_PASSWORD 已失效，可手工删除
#    （.env 不入库，删不删都不影响功能）

# ③ UAT 走查工单（FW20260922-0059 / 0060）**保留** —— 它们是走查证据。
#    若要清理，先确认已截图归档。
```

`--disable` 的实际动作：

| 动作 | 效果 |
|---|---|
| `DELETE FROM store_users` | 撤掉临时门店映射 → **数据范围归零** |
| `DELETE FROM "rolesUsers"` | 撤销业务角色 → 无任何业务权限 |
| `password` 重置为随机哈希 | 旧口令失效，不可知 |
| `username` / `email` / `nickname` 改为 revoked 形态 + 打 `uat_restricted_at` 标记 | **阻断登录入口**（唯一约束保证不撞车） |
| **保留 `users` 行** | 工单 handler 与事件 operator 的历史引用**继续可解释** |

> 结果：临时账号**已无法继续工作**、下一轮不会被误认成真实员工、审计引用仍指得回 UAT-A。
> 真正需要清库时，**先确认工单与事件引用已归档**，再 `--delete`；
> 若仍有引用，脚手架会**拒绝**物理删除（需显式 `--delete --force` 才放行）。

> ⚠️ **临时账号必须在走查结束后停用**（复核方 2026-09-21 / 2026-09-22 裁定）：
> 留在系统里，下一轮验收就无法区分"这是临时账号还是真实售后人员"。
> 正式 `storeUsers` 名单到位后再播种正式账号。
