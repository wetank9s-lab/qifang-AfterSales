## 5. 观察项（除 §2 的 8 步之外，必看）

### ① 自动生成的「编辑 / 删除」按钮是否误导 —— **本轮重点盲测项**

背景：NocoBase 页面编译器会强制合并 `addNew` / `bulkDelete` / `view` / `edit` / `delete`
五个动作，**无法通过蓝图移除**（DEV-53 坑 2）。

**已核实的事实（供判定参考，不进主持人台词）**：
- 这两个角色对 `serviceTickets` **只有 `get` / `list` / `view`**，**没有 `update` / `destroy`**
  → 点下去必然被服务端拦（非 403 即错误提示）；
- 也就是说：**不存在写入漏洞**，这是**纯 UX 问题**。

| 观察点 | 记录 |
|---|---|
| 真人**是否**把「编辑」理解成"处理这张工单"并点击？ | ⬜ 是 / ⬜ 否 |
| 是否**先点「编辑」而没找到「受理」**？（说明「受理」不够显眼） | ⬜ 是 / ⬜ 否 |
| 若误点，界面提示是否**看得懂**？（原文？还是笼统"操作失败"？） | ____________________ |
| 误点后**能否自行回到**正常流程？ | ⬜ 能 / ⬜ 否 |

## 9. 走查结束后的清理（**必做**）

> ⚠️ **走查后默认执行 `--disable`，不要执行 `--delete`**（首轮已裁定）。

**为什么不是直接物理删除**：走完第 2 步之后 UAT-A 通常已是主工单的 `handler_user_id`，
受理 / 派工 / 改派 / 改约每条 `ticket_events` 的 `operator_user_id` 也指向它。
而 UAT 工单是**要保留的验收证据**。此时物理删除用户行，会让工单与事件的引用变成空引用 ——
证据"还在"，但**说不清是谁做的**，审计上不可解释。

本项 NocoBase 的 `users` 表**没有**可用的禁用字段，因此按降级口径执行：

```bash
# ① 【默认】停用：撤角色 + 撤门店映射 + 重置随机口令 + 阻断登录，**保留 users 行**
node scripts/uat-accounts.mjs --disable

# ② .env 里残留的 UAT_*_PASSWORD 已失效，可手工删除
#    （.env 不入库，删不删都不影响功能）

# ③ UAT 走查工单（FW20260922-0059 / 0060）**保留** —— 它们是走查证据。
#    若要清理，先确认已截图归档。
```

| `--disable` 动作 | 效果 |
|---|---|
| `DELETE FROM store_users` | 撤掉临时门店映射 → **数据范围归零** |
| `DELETE FROM "rolesUsers"` | 撤销业务角色 → 无任何业务权限 |
| `password` 重置为随机哈希 | 旧口令失效，不可知 |
| `username` / `email` / `nickname` 改为 revoked 形态 | **阻断登录入口** |
| **保留 `users` 行** | 工单 handler 与事件 operator 的历史引用**继续可解释** |

## 附：走查不需要培训，但需要一句开场

> "请在列表里找到 `FW20260922-0059` 这张报修单，**把它受理，然后派给王师傅**。"
>
> ⚠️ 必须报出工单号（同店还有 2 张 `NEW` 单，不点名可能处理错单）。
> **报工单号只是指定对象，不是提示操作方式** —— "点哪里"仍然不能说。
>
> 然后**闭嘴看着他操作**。他找不到按钮、点错地方、看不懂文案 —— 这些都是要走查的结果，
> 不是需要你立刻纠正的错误。开发人员站在旁边说"点这里、再点那里"，
> 只能证明功能存在，证明不了后台能用。
>
> **本轮特别提醒**：**不要**事先告诉他"编辑/删除不能用"。
> 他会不会被那两个按钮带偏，本身就是本轮要测的东西（见 §5 观察项 ①）。
