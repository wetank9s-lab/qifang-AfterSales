## 1. 运行时依赖核实（用户要求"先核实运行时依赖"）

| 项 | 结论 |
|---|---|
| 实际版本 | 容器内 `/app/nocobase/node_modules/xlsx` = **0.20.3**（实测 `XLSX.version` 与 package.json 一致） |
| 许可 / 入口 | Apache-2.0，`main: xlsx.js`（CommonJS） |
| 来源 | **NocoBase 镜像自带的传递依赖**，不是本项目显式安装的 |
| 适用安全公告 | **CVE-2023-30533**（原型链污染，读恶意文件触发）影响 `< 0.19.3`；**CVE-2024-22363**（ReDoS，读恶意文件触发）影响 `< 0.20.2` ⇒ **0.20.3 两个都不命中** |
| ⚠️ 供应链陷阱 | SheetJS **已停止向 npm 发布**，注册表**永远停在 0.18.5**（两个 CVE 都命中）。⇒ 任何 `npm i xlsx` 都会把版本降到不安全区间 |
| ⚠️ 扫描器陷阱 | GitHub Advisory 这两条只有 `introduced: 0`、**没有 `fixed` 事件**（npm 生态里没有可以指名的修复版本）⇒ osv-scanner / Dependabot / Snyk 会**永远**把 0.20.3 标为受影响（**误报**）。`npm audit` / Trivy / Grype 按 range 匹配，0.20.3 干净 |
| 宿主机测试副本 | 已从 **SheetJS 官方 CDN 锁定 tarball** 装到隔离工作区：`~/.workbuddy/binaries/node/workspace/node_modules/xlsx@0.20.3`（**不走 npm**） |

### 处置：外置复用 + 运行时版本守卫

- `xlsx` 加进 `build-plugin.mjs` 的 `EXTERNALS`（**保持外置**，复用容器内那份 0.20.3），
  产物里留下 `require("xlsx")`，**没有**把库打进 bundle（验收脚本断言这一点）。
- 新增 `historical-import/version-guard.ts`：真正解析前校验 `XLSX.version >= 0.20.2`，
  不满足就抛 `DEPENDENCY_UNSAFE_VERSION` **拒绝解析**，而不是静默用一个有 CVE 的解析器读客户文件。
  ⇒ 镜像升级把 xlsx 换旧 / 删掉时，会以明确错误码失败，不会静默降级。

> **为什么没选"自己装一份打进产物"**：那反而更容易落到 npm 的 0.18.5（有漏洞）。
> SheetJS 官方推荐的做法是**锁定 CDN tarball**；而"复用镜像内已验证的 0.20.3 + 运行时守卫"
> 在本项目约束下更稳（镜像由 NocoBase 官方维护，版本只可能更新不会回退到 0.18.5）。
> 代价是耦合到传递依赖 —— 已按 `@napi-rs/canvas`（DEV-84）同类方式**显式声明 + 门禁盯着**。

## 3. 限额与拒绝（用户第 4 条）

上限集中在 `historical-import/limits.ts`（唯一事实来源，所有入口从这里取）：

| 上限 | 值 | 理由 |
|---|---|---|
| 单文件字节 | 20 MB | 真实样本 59 KB ~ 209 KB；20 MB 已远超正常门店月度表 |
| 解压后总字节 | 200 MB | zip 膨胀保护 |
| 单条目压缩比 | 200:1 | 同上 |
| 工作表数 | 40 | 真实样本最多 3 张 |
| 单表数据行 | 20 000 | 真实样本最多 831 |
| 整簿数据行 | 60 000 | — |
| 列数 | 256 | 真实样本最多 256（欣盛 `9月`） |
| 单元格文本 | 2 000 字符 | 超出截断并计数，不整批失败 |
| 一格多号 | 6 个 | — |
| 表头探测行数 | 10 | 真实样本最多 2 |

**不做的事**（用户原话「不得执行 Excel 公式、宏或外部链接」）：
读工作簿时显式传 `cellFormula:false / cellHTML:false / bookVBA:false / bookDeps:false / bookFiles:false`。
SheetJS 读时**只取缓存值、不计算公式**，且本插件没有任何导出/回写电子表格的路径。

⚠️ **能力边界（如实写明）**：`XLSX.read()` 是**同步**的，一旦进入无法中断。
所以"长时间阻塞"真正的防线是**前置的字节上限 + zip 膨胀上限**；
`PARSE_TIMEOUT_MS` 只能在**工作表边界**检查，超时就拒绝并返回已完成的报告。

## 5. 能力边界（用户 2026-10-12 点名要求准确记录）

1. **`verify-types` 不是"TypeScript 全量零诊断"检查。**
   它只对两类判红：**TS2304/TS2552（未声明标识符）** 与**宿主包具名导入白名单违例**。
   其余诊断（当前 **112 条**，主要是宿主包 stub 引发的 TS2339/TS2694/TS2741…）
   **如实打印但不判红** —— 那是已知积压，需要单独排期，
   ⛔ **不得**把这 112 条说成"已解决"，也不得把"门禁通过"说成"类型全对"。
2. **TS2300 是类型错误，不是"合法写法"。**
   `src/server/services/photo-service.ts` 有两条内容重复的
   `import { … } from '../../shared/media-guard'`（12 条 TS2300）。
   它在 ES/TS 里有明确语义（绑到同一个值），运行期与构建都无影响，
   但**仍是类型错误**，登记为**待精确修复**（合并两条 import），
   ⛔ **不得**标为"合法"或"已知可接受"。
3. **本轮解析只到"原始 + 标准化候选 + 报告"为止。**
   字段映射交互、预览、去重、正式导入、转当前服务单**都还没做**；
   15 家门店与系统 code 的映射仍未核定 ⇒ **未确认门店禁止写入数据归属**。
4. **SheetJS 读值是同步的**，墙钟上限只能在表边界检查（见 §3）。

## 6. 过程中两个值得记的坑

1. **七份真实样本一度不在本机**（`C:\Users\Administrator\Desktop\售后数据\` 已空）。
   旧会话的 `probe.py` / `probe_out.txt` 里保留了原始路径与全部工作表结构，
   据此反查出七份文件名与 `E:\桌面文件整理\售后系统\` 才是当前位置。
   ⇒ 教训：**探测输出要连"样本来自哪里"一起记**，否则样本一移位置就得从头猜。
2. **验收脚本自己的两处判据错误**（比产品缺陷更隐蔽）：
   - 版本比较的正则写成 `\\.`（双反斜杠）⇒ 匹配"字面反斜杠 + 任意字符" ⇒ **恒 false**，
     而产品其实是好的（0.20.3）。
   - "xlsx 没被打进产物"用"有没有出现 SheetJS 这个词"判断 ⇒ 我们**自己的错误消息**
     里就写着"解析器 xlsx（SheetJS）不可用" ⇒ 同样**恒 false**。
     ⇒ 已分别改成数值三段比较与"库 banner（`http://sheetjs.com`）"判据。
   - 教训：**判据自己写错，比没有判据更危险**（与 DEV-140 同型）。
