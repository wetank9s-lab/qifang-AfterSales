### 处置：外置复用 + 运行时版本守卫

- `xlsx` 加进 `build-plugin.mjs` 的 `EXTERNALS`（**保持外置**，复用容器内那份 0.20.3），
  产物里留下 `require("xlsx")`，**没有**把库打进 bundle（验收脚本断言这一点）。
- 新增 `historical-import/version-guard.ts`：真正解析前校验 `XLSX.version >= 0.20.2`，
  不满足就抛 `DEPENDENCY_UNSAFE_VERSION` **拒绝解析**，而不是静默用一个有 CVE 的解析器读客户文件。
  ⇒ 镜像升级把 xlsx 换旧 / 删掉时，会以明确错误码失败，不会静默降级。

> **为什么没选"自己装一份打进产物"**：那反而更容易落到 npm 的 0.18.5（有漏洞）。
> SheetJS 官方推荐的做法是**锁定 CDN tarball**；而"复用镜像内已验证的 0.20.3 + 运行时守卫"
> 在本项目约束下更稳（镜像由 NocoBase 官方维护，版本只可能更新不会回退到 0.18.5）。
> 代价是耦合到传递依赖 —— 已按 `@napi-rs/canvas`（DEV-84）同类方式**显式声明 + 门禁盯着**。

### 1.1 🔴 附带踩到并堵上的坑：仓库根被留下 `package.json`

2026-10-12 实测：一次 npm 操作在**仓库根**留下了 `package.json`
（内容 `{"dependencies":{"xlsx":"^0.18.5"}}`）+ `package-lock.json`。

为什么这是**红灯级**而不是"清理一下就好"：

- `^0.18.5` 正是 npm 注册表上 xlsx 的**最后一个版本**，两个公开 CVE 在它上面**都未修复**；
- Node 的模块解析会**优先**走仓库根的 `package.json` / `node_modules`，
  于是"顺手 `npm i`"会把依赖悄悄降到不安全区间，
  而**构建照样成功、运行时照样能解析** —— 没有任何断言会红。

⇒ 已在 `scripts/build-plugin.mjs` 的预检里加守卫：仓库根一旦出现
`package.json` / `package-lock.json` 就**拒绝构建**（本项目的依赖必须装在隔离工作区）。
反向验证：注入 `{"dependencies":{"xlsx":"^0.18.5"}}` ⇒ 构建 `exit=1` 并指名该文件；删除后恢复 `exit=0`。

## 3. 限额与拒绝（用户第 4 条）

上限集中在 `historical-import/limits.ts`（唯一事实来源，所有入口从这里取）：

| 上限 | 值 | 理由 |
|---|---|---|
| 单文件字节 | 20 MB | 真实样本 59 KB ~ 209 KB；20 MB 已远超正常门店月度表 |
| 解压后总字节 | 200 MB | zip 膨胀保护 |
| 单条目压缩比 | 200:1 | 同上 |
| 工作表数 | 40 | 真实样本最多 3 张 |
| 单表数据行 | 20 000 | 真实样本最多 831 |
| 整簿数据行 | 60 000 | — |
| 列数 | 256 | 真实样本最多 256（欣盛 `9月`） |
| 单元格文本 | 2 000 字符 | 超出截断并计数，不整批失败 |
| 一格多号 | 6 个 | — |
| 表头探测行数 | 10 | 真实样本最多 2 |

**不做的事**（用户原话「不得执行 Excel 公式、宏或外部链接」）：
读工作簿时显式传 `cellFormula:false / cellHTML:false / bookVBA:false / bookDeps:false / bookFiles:false`。
SheetJS 读时**只取缓存值、不计算公式**，且本插件没有任何导出/回写电子表格的路径。

⚠️ **能力边界（如实写明）**：`XLSX.read()` 是**同步**的，一旦进入无法中断。
所以"长时间阻塞"真正的防线是**前置的字节上限 + zip 膨胀上限**；
`PARSE_TIMEOUT_MS` 只能在**工作表边界**检查，超时就拒绝并返回已完成的报告。

## 8.2 双层存储：为什么是三张表

```
historical_import_batches     一次上传的事实（文件哈希 / 上传者 / 可见范围 / 归属状态 / 当前映射版本）
        │
        ├── historical_import_rows        **原始层**：只追加。Excel 原始行号 + 原始单元格值 + 稳定源标识
        │
        └── historical_import_candidates  **标准化层**：按 mapping_version **分代**，旧版本不删
```

三条结构性约束（靠 DB 唯一索引保证，不靠调用方自觉）：

| 约束 | 索引 | 它挡住的事 |
|---|---|---|
| 同一批次内同一张表的同一原始行只有一条 | `unique(batch_id, sheet_name, source_row)` | 重复解析把原始层堆成两份 |
| 同一原始行在同一映射版本下只有一条结果 | `unique(row_id, mapping_version)` | 重跑把同一代写两遍 |
| 批次号唯一 | `unique(batch_no)` | 口头核对时指向不明 |

**分代留痕的实测**（`verify-historical-import.mjs` ⑥）：同一批次连续暂存两次 ⇒
库内 `mapping_version` 两代**并存**（如 `v14|105` 与 `v15|105`）；
而原始层行数两次之后**一个都没变**。变异自证 M3 会把这条断言**真的判红**（见 8.5）。

## 8.3 分类与映射**结构性解耦**（东山的 849 行）

用户原话：「东山的 849 条销售配送记录，不得因为门店人员重新映射了字段就变成售后业务。」

落地方式不是"记得别那么做"，而是**让 `disposition` 的计算根本不读映射**：

```ts
// mapping.ts —— 分类只读 sheetClass，不读 mapping
const isServiceSheet = sheetClass === 'service-install' || sheetClass === 'service-repair';
const isSalesSheet   = sheetClass === 'sales-or-delivery';

if (isSalesSheet) {
  disposition = 'excluded';
  reason = '这张表按表头结构判定为销售/配送资料，整表不进售后';
}
```

`sheetClass` 来自 `parse.ts` 的 `classifySheet()`（表头**结构信号**），与"某列被映射成什么字段"无关。

**验收里的"伪装映射"用例**：把东山的「购机日期」映射成"接件日期"、把「物流送货人员」
映射成"服务人员" —— 这是"用改映射把销售记录伪装成售后"的最直接尝试。
结果 `excluded=849 / importable=0`，**849 行一条都没进售后**。
变异自证 M1 会把这条断言**真的判红**（见 8.5）。

## 9.1 A 三项针对性核对（逐条）

### A.1 「异常命中次数」≠「涉及的唯一原始行数」

用户原话：「多手机号、含糊日期、缺手机号、服务结果异常**可能同时出现在同一行**，
不得简单求和并称为唯一异常行数。」

修法：`SheetQuality` 增加两个**并列**字段（不是把和当成行数）：

```
anomalyHits        = 四项之和（命中次数，同一行可命中多类）
rowsWithAnyAnomaly = 至少命中一项的行数（每行最多算一次）
```

实测（`verify-historical-ledger.mjs` **22/22**）：

| | 多手机号 | 含糊日期 | 缺手机号 | 服务结果异常 | **命中次数** | **唯一行数** | 差 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 合计 | 215 | 1290 | 118 | 569 | **2192** | **2076** | **116** |

其中康乐 Sheet2 的差最大：缺手机号 104 + 服务结果异常 105 = 209 次命中，只涉及 **105 行**。

## 9.3 C 去重预览

- **同文件重复上传**：遵守权限隔离 + 幂等（见 A.2）。
- **跨文件疑似重复**：按「手机号 + 姓名 / 业务日期 / 家电型号」联合判断。
  🔴 **不得只凭手机号**：只命中手机号 ⇒ `weak`；再有姓名/日期/型号之一 ⇒ `strong`。
  实测：**强证据 亦有、弱证据亦有**，且弱证据恰好是"同号不同型号不同日期"
  （同一客户可能有多次真实售后）。
- **不合并、不删除**：响应里原话写着"仅提示…不会自动合并、不会删除任何原始记录"；
  人工裁决只有 `keep-both` / `mark-duplicate` 两个动作，都只写"人的意见"。
- **不跨店泄漏**：扫描范围限定在 `listBatchesForActor` 可见的批次内；
  验收断言"B 门店的去重扫描看不到 A 门店的批次"。

## 9.4 D 受控历史归档闭环

### 独立档案（不是工单）

新表 `historical_service_archives`，与 `service_tickets` **结构上分开**。
为什么不"在工单上加个 isHistorical 标记"：那样所有按 status 的看板会**自动**把历史算进去
（SLA 分母被污染）、状态流转会**默认**对历史可用 —— 而"它不是工单"只存在于注释里。
分表之后"历史不污染当前"是**结构性的**：SLA 巡检扫的是 `service_tickets`，看不见本表。

### 归档前的四道校验（逐条对应用户 D 条）

| 用户要求 | 实现 | 验收证据 |
|---|---|---|
| 验证当前上传批次权限 | `getBatchForActor`（越权一律 404） | 未登录 401；B 对 A 的批次归档 404 |
| 验证正式门店 code 与真实门店身份的确认关系 | `assertStoreConfirmed(code, scope)` | 名单外门店 ⇒ 409 `STORE_IDENTITY_UNCONFIRMED`；对只有演练范围的门店发起**正式**归属 ⇒ 409 `STORE_IDENTITY_DRILL_ONLY`；门店账号自己确认归属 ⇒ 403 |
| 验证映射版本 / 异常处理状态 / 人工确认 | `assertReadyToArchive` + `mapping_version` | 还有待处理记录时归档 ⇒ **409 `REVIEW_PENDING`**（且这条断言必须跑在"确认完"**之前**，顺序本身是判据的一部分） |
| 保留来源文件/工作表/原始行/标准化版本关联 | 档案上的 `batch_id / row_id / source_file_name / source_sheet / source_row / mapping_version` | 断言"每条档案都能回答来自哪个文件哪张表哪一行哪一版"（`2/2`） |
| 重复点击、网络重试不生成重复档案 | `idempotency_key = sha256(批次\|源标识\|映射版本)` **UNIQUE** | 重复归档 ⇒ `created=0 reused=2`，库内档案数不变 |
| 历史与当前 SLA/KPI 隔离 | 分表 + 归档不写 `service_tickets` | 断言"当前工单数不因归档变化" |

另外：**非售后排除记录不进档案**（断言 `0 条`）。

### 「转为当前服务单」——单独操作、不批量

`historical_ticket_conversions`：`archive_id` **UNIQUE** ⇒ 一条档案最多转一次
（把"**不得批量自动转单**"变成**结构约束**）。接口**不接受数组**（传 `archiveIds` ⇒ 422）、
**必填理由**（少于 4 字 ⇒ 422）、仅总部可调（门店账号 ⇒ 403）。
验收实测：单条转单成功并带回来源关联（`archiveNo / mappingVersion / sourceFileName / sourceSheet / sourceRow`）；
重复点击 ⇒ `reused=true` 且**工单数不再增加**。

### 🔴 真实历史资料**结构上无法**被正式归属

用户原话：「因为当前 15 家门店 code 尚未全部核定，**真实历史资料不得未经确认就正式归属**。」

落地：门店身份确认名单放在 `service_settings` 的
`historical.store-identity-confirmations`，每项带 `scope: 'drill' | 'production'`。
**迁移只写入 S01 / S02，且都是 `scope: 'drill'`** —— 它们是已核定授权的验收账号
（UAT-A / UAT-B）所绑定的门店，用于**合成文件**演练。
⇒ 当前**没有任何** `production` 条目，所以：

```
真实七份样本批次 23 个 → 已确认归属 0 个 → 已归档档案行 0 行
门店身份名单里 production 条目 0 条
```

这三条都是**门禁断言**，不是承诺。演练归属在批次备注里留痕（`[attribution:drill]`），可一眼分辨。
